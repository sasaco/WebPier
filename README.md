# WebPier 鉄道橋脚の荷重計算

`pre/input.json`（schema 2）を読み、0500 直接基礎の地盤ばね、0600 上部工反力・橋脚自重、0610 線路方向荷重、0620 直角方向荷重、0710 地震時の線路方向荷重、0720 地震時の線路直角方向荷重を計算し、A4縦・白黒の計算書PDFと結果JSONを作成します。0610・0620 からは FEMPython / FrameWebforCS の入力、0710・0720 からは JRSNAP 5.2-L03 の入力（NDU）も作成します。

計算はPython、計算書の組版は GridLayoutPdf、PDF描画はその ReportLab バックエンドです。実行時に Excel や元の xls・PDF は使いません。**構造解析による組合せ応答、部材の断面照査、寸法・配筋の最適化は対象外**です。

用語は [CONTEXT.md](CONTEXT.md)、原則は [docs/adr/](docs/adr/)、決定事項は [.claude/docs/plans/refactoring-decisions.md](.claude/docs/plans/refactoring-decisions.md) を正とします。

## 実行

Windows専用です。リポジトリのルートで実行します。初回は `uv` がPythonと依存ライブラリを準備します。

```powershell
uv run --project "." --locked python -m webpier                     # 全段階（--stage all）
uv run --project "." --locked python -m webpier --overwrite         # 既存の成果物を更新する
uv run --project "." --locked python -m webpier --stage 0610 --overwrite
uv run --project "." --locked python "./run_design.py" --overwrite  # python -m webpier と同じ
```

| 引数 | 意味 |
|---|---|
| `--stage {0500,0600,0610,0620,0710,0720,all}` | 計算する段階。既定は `all`。依存する段階は内部で計算するが、その成果物は書かない |
| `--overwrite` | 既存の成果物を置き換える。指定しないと、既存の成果物があれば何も書かずに止まる |
| `--input` | 入力JSON（既定 `pre/input.json`） |
| `--output-dir` | 計算書・結果JSONの出力先（既定 `output`） |
| `--post-dir` | 外部ソフト向け入力と付帯JSONの出力先（既定は出力先と並ぶ `post`） |

終了コードは、0 が公開完了、2 が入力・出力先・環境のエラーで何も公開していない、3 が公開に失敗して旧成果物の一部を復元できなかった場合です（退避ファイルの場所を表示します）。

| 段階 | 依存 | `output/` | `post/` |
|---|---|---|---|
| 0500 | — | `0500_直接基礎.pdf` / `.json` | — |
| 0600 | — | `0600_上部工反力.pdf` / `.json` | — |
| 0610 | 0500, 0600 | `0610_線路方向荷重.pdf` / `.json` | `線路方向.json` と付帯JSON |
| 0620 | 0500, 0600 | `0620_直角方向荷重.pdf` / `.json` | `線路直角方向.json` と付帯JSON |
| 0710 | 0500, 0600, 0610 | `0710_線路方向荷重.pdf` / `.json` | `線路方向.ndu` と付帯JSON |
| 0720 | 0500, 0600, 0620 | `0720_線路直角方向荷重.pdf` / `.json` | `線路直角方向.ndu` と付帯JSON |

`--stage all` は12の計算書・結果JSONと、FrameWeb入力2つ・JRSNAP入力（NDU）2つ・付帯JSON4つの計20ファイルをまとめて更新します。外部ソフト向けの入力は段階の成果物なので、その段階を選べば常に書きます（決定42）。0710・0720 を含む生成は JRSNAP の解析設定が必須で、空欄や誤りがあれば入力エラーで止まります。入力エラーは計算書を描く前に出ます。付帯JSONは `<ファイル名>.provenance.json` です。`output/`・`post/` は生成物なので git で追跡しません。

書体は `%WINDIR%/Fonts` の `msmincho.ttc`・`msgothic.ttc`・`calibri.ttf`・`timesi.ttf` を使います。本文はMS明朝9.9pt、見出しはMSゴシック9.9pt、添字は6.5ptです。必要な書体や文字がなければ生成を停止します。

## 入力（schema 2）

`pre/input.json` は `schema_version: 2` です。parser（`webpier/inputs/parse.py`）は入力を一度だけ検査し、各段階はその結果を共有します。

- **知らないキーは入力エラー**です。旧形式の読み替えはしません。
- **値を補いません。** 計算に要る値が空欄（`null`）なら入力エラーです。`0` は数値です。全項目が空欄の支承枠だけは「空き支承枠」（CONTEXT.md）として除外し、L3・L4 は空欄（2線まで、決定23）とします。
- **選択肢はプログラムが持ちます**（`webpier/inputs/choices.py`）。入力JSONには選んだ値だけを保存し、一覧にない値は入力エラーです。車両名は `EA-17`（EA-17の規定式で制動・始動）と `P-16`（軸重式）、土質区分は「砂質土」「砂礫」「粘性土」「砂質土と粘性土の互層」、杭種は「直接基礎」「場所打ち杭」（場所打ち杭は未対応の入力エラー）、鉄筋の材質は SD295・SD345・SD390 です。
- **派生値は入力にしません。** 表層の層厚（H6＋H5＋min(df1, df2)）、排除した土の単位体積重量（表層の湿潤）、B・C支点の合計は計算器が求めて印刷します。支承位置 f は両側とも入力します。
- **入力値は印字桁に丸めてから入力します。** 印字桁より細かい値は黙って丸めず、入力エラーにします。桁は入力票（`.claude/docs/Example橋脚/pre/input-*.pdf`）に合わせています。

| 項目 | 桁 |
|---|---|
| 寸法 B・W・H、df、水位、桁長・スパン、h1〜h4、hs、f、軸距、車両長、車両高、支承位置、層厚 | 小数3桁（m） |
| D1・D2・雪荷重、軸重 | 小数2桁（kN）。地震時列車荷重は小数2桁（kN/m） |
| 分担率 L1〜L4、衝撃係数、荷重修正係数、復旧性制動係数 | 小数3桁 |
| 摩擦係数 μ | 小数2桁 |
| 単位体積重量 | 小数1桁（kN/m³） |
| 曲線半径・列車速度・斜角 θ、N値・qu・Ed | 整数 |
| 内部摩擦角 φd | 小数1桁（°） |
| コンクリート強度 | 小数1桁（N/mm²） |

- 杭（杭種以外の杭の項目・杭の配置・杭の単位体積重量）、斜角、遠心の作用方向、梁の詳細位置は、近い将来の機能のための予約項目です。計算には使わず、形式と桁だけを検査します（決定19）。`出典` は検査しない自由記述です。
- `復旧性制動係数` は側ごとの任意入力です。入力すると復旧性の制動係数としてそのまま使い、空欄なら安全性の ρu×γB を使います。Example2 07 p.7-11 の終点側は 1.0 を入力します。
- `jrsnap_longitudinal`・`jrsnap_transverse` は方向ごとの JRSNAP の入力条件です。`shear_factor_vcd`・`shear_factor_vsd`・`shear_factor_vdd`（部材係数 γb、0より大きく99.99以下）、`aggregate_max_mm`（粗骨材最大寸法、0.1〜999999 mm）、`analysis_steps`（荷重増分の分割数、整数）、`limited_final_step`（制限ステップ、分割数以下）、`target_displacement_m`（目標変位、0.001 m 単位で0以外。符号は地震の向きと同じ）です。0710・0720 の生成に必須で、見本値で補いません。0500〜0620 だけを選ぶ生成には使いません。
- 鉄筋（`鉄筋`）は全キーが必須です。空欄は未入力として保存でき、柱の配置と JRSNAP 出力が値を要するときにパス付きの入力エラーになります。

## 計算の原則

- **元Excelの誤りは再現しません**（ADR-0001）。WebPier は元Excel（0500〜0720のxlsと転記VBA）を基にしていますが、正規の計算は工学的に正しい式を使います。元式を意図的に残す箇所は、下の互換一覧に理由とともに書いたものだけです。
- **物理量で計算します**（ADR-0002）。元Excelのセル番地、セルの再生、元Excelから採取した照合値は使いません。期待値は Example2 の原資料から独立に転記した値と、実装を使わない手計算だけです。
- **印字桁で計算します**（ADR-0003）。計算書に印刷する値は内部でも印字桁に丸め、後続の計算はその丸めた値を使います。合計・積は印刷された部分の値から求め（0.125 の3行は各 0.13、合計 0.39）、段階間の引継ぎも前段の計算書に印刷された値で行います。印刷しない中間値は作りません。例外は移動荷重の載荷位置の探索で、探索の内部は丸めず、採用した結果を印字桁に丸めて印刷します。丸めは四捨五入（0.5は絶対値の大きい側）だけで、VBA の Single 精度、Excel の ROUND、偶数丸めは使いません。印字桁は計算器（`webpier/calc`）が値ごとに持ち、帳票は丸め直しません。
- **欠けた値を補いません**（決定5）。計算中に成立しない条件（0除算、表の範囲外など）も入力エラーにします。例：コンクリートのヤング係数 Ec は f'ck 18〜80 N/mm² の表の線形補間だけで、範囲外は入力エラー（決定25）。複線の衝撃低減 1 − L/200 は L ≥ 200 m を入力エラー（決定13）。

### 互換一覧

元Excelの式を意図的にそのまま再現する箇所（**元式の互換動作**、CONTEXT.md）の一覧です。元Excelを意図して再現する箇所は、必ずここに理由とともに書きます（ADR-0001）。ここにない元Excelとの差は、すべて誤りとして直したものです。

いまは**ありません**。以前の4点のうち、可動支承の水平力の下限 μ·T/n は正しい設計式として本文の規則にし（決定11）、残る3点（柱下端の集計の桁受けを重量で集計、直角方向のモーメントに桁受けを含める、上載土の xL に線路方向の重心を使う）は元Excelの誤りとして直しました（決定20）。

## 構成

### 層別パッケージ（ADR-0004）

```
webpier/
  core/       Printed（印字桁つきの値）、厳密なJSON読込み、エラー、ハッシュ
  inputs/     schema 2 の解析と検証。項目表 fields.py、選択肢 choices.py
  calc/       段階の計算（foundation, reaction, longitudinal, transverse, seismic_*）と共通の骨組・移動荷重
  reporting/  GridLayoutPdf による計算書（stages/ に段階ごとの組版）
  export/     frameweb/（FEMPython・FrameWebforCS）、jrsnap/（JRSNAP 5.2-L03 NDU）
  pipeline/   段階の登録表、生成、公開、CLI（python -m webpier）
  gui/        入力エディタ（python -m webpier.gui）
```

依存は `core ← inputs ← calc ← reporting / export ← pipeline ← gui` の向きだけです。`tests/test_layer_boundaries.py` が強制し、calc・inputs・core は描画や Tk のライブラリも import しません。計算は帳票に依存しません。

### 段階の登録表

段階の依存・計算・帳票・成果物・外部出力は `webpier/pipeline/stages.py` の `StageSpec` の表1か所に定義します。生成・CLIの選択肢・成果物の一覧はすべてこの表から作るので、段階や外部出力の追加は表の1項目です。`calculate` と `render` には宣言した依存段階の結果だけを渡すので、宣言していない依存は動かずに失敗します。

### 生成と一括公開

1. 段階と出力先をすべて検査してから始めます。同名のディレクトリやシンボリックリンク、入力と同じパスの出力は拒否します。
2. 入力を一度だけバイト列で読み、厳密に解析します（重複キー・NaN・Infinity は入力エラー）。そのSHA256を全ての結果JSONと付帯JSONに記録します。
3. 選択した段階と依存段階をすべて計算してから描画します。保存済みの結果JSONは読みません。
4. 計算書・結果JSON・外部ソフト向け入力・付帯JSONを各出力先の横でステージングし、`webpier/pipeline/publication.py` がまとめて公開します。旧ファイルを同じファイルシステム内に退避して置き換え、公開した実バイト・入力・実装の同一性を最後に確かめます。失敗すれば旧ファイルをすべて戻し、その実行で新しく作ったファイルは消します。複数ファイルがOS上で一瞬に切り替わる仕組みではありません。
5. 強制終了や復元の失敗では、出力先ごとの `.webpier-*` に `publication-pending`・`publication-journal.json` と退避ファイルを残し、次の実行はそれを見つけて止まります。journal の各 `destination`・`backup`・`had_original` を照合して旧成果物を戻すか、一式を別の場所へ保全してから再実行してください。

結果JSON（`output/<段階>.json`）は `schema_version`・`stage`・`input`（ファイル名とSHA256）・`implementation_sha256`・`result` を持ちます。付帯JSON（`post/*.provenance.json`）は、その外部入力のファイル名とSHA256、入力のSHA256、実装のSHA256、選択した段階、同じ世代の全成果物（役割・出力先・ファイル名・SHA256）を記録します。実装のSHA256は、`webpier` のソースと、インストール済みの GridLayoutPdf・ReportLab・Pillow・書体ファイルのバイトから求めます（`webpier/pipeline/runtime.py`）。生成中にこれらが変わると公開しません。

PDFは作成日時を含まないので、同じ入力・書体・ライブラリからは毎回同じバイトになります。

## 計算書

全6帳票はA4縦・白黒で、体裁は `.claude/docs/Example橋脚/output` の書体・字下げ・等号の位置・表の行高を基準にし、数値・式・ケースは現在の入力から計算します。計算内容の見本は `.claude/docs/Example橋脚2` です。式・表・図のまとまりを保って改ページするので、ページ数は内容に応じて変わります。文字の縮小や伸縮で固定ページ数に収めることはしません。体裁の契約と測定方法は [.claude/docs/reporting-style.md](.claude/docs/reporting-style.md) にあります。

各帳票の内容は Example2 の対応する計算書に合わせています（0500: 04 地盤のモデル化、0600: 05・07、0610: 08、0620: 09、0710: 10、0720: 11）。

- 0500 は地盤ばね（kv・Kv・ks・Ks・Kr、長期・短期、2方向）と支持力係数（解説表13.2.2.3-2、表の中間は線形補間、42度以上は Nγ=150・Nq=85）を計算し、土質区分の係数・指数を印刷します。平坦な一層の土被りでは、JRSNAP に渡す有効根入れ深さ Df と平均有効単位重量 γ2 = ((Df − hw2) × γwet + hw2 × γsub) / Df も印刷します（CONTEXT.md）。
- 0600 は死荷重・雪荷重（2・10・30年確率）、橋脚自重・上載土・浮力、移動荷重の反力、方向別の荷重を計算します。桁受けは体積 V = 0 のとき、その項と集計表の行を省き、後続の項の番号を詰めます。本橋脚の支承の表は空き支承枠を除き、支承は入力の枠の番号（G1〜G10）で示します（決定41）。
- 0610 は20基本ケース・20 Define・16組合せ・8抽出、0620 は17基本ケース・15 Define・16組合せ・8抽出です。組合せは「用途別解決」として、各成分を印刷された係数×印刷された基本作用で求め、N・H・M・q ごとに一度だけ印字桁に丸めます。0620 の単線の成分は組合せの中で上り線・下り線のどちらか一方にそろえ、車両横荷重と風の正負は独立に選びます。
- 0710 は8基本ケース・1組合せ（地震は起点側 ← の片方向）、0720 は9基本ケース・上り線・下り線それぞれの2組合せ（地震は → の片方向）です（決定21・30）。どちらも柱下端の0.010 mの微小部材（CONTEXT.md）を骨組図に示します。
- Example2 にあっても印刷しないもの（決定41）：0610 の荷重図。0710・0720 のばね（骨組図のばね記号、Kv・Ks・Kr、ばねの表と数値。Example2 10-7・11-7 の節点ばね分布図にあたる）と荷重図、0720 の柱下端の拡大図。節の番号は詰めます（0610 の組合せは 8.3、0710 は 10.3、0720 は 11.3）。ばねを示さないことは、固定基礎や解析可能な支持条件を意味しません。

## 外部ソフト向けの入力

### FrameWeb（FEMPython / FrameWebforCS）

0610 から `post/線路方向.json`、0620 から `post/線路直角方向.json` を作ります。形式は Example2 の FrameWeb 保存ファイル（`.claude/docs/Example橋脚2/08_線路/frameWebForJS.json` など）に合わせています。規則の詳細は `webpier/export/frameweb/` の各モジュールに書いています。

- 荷重ケースごとに地盤ばねの組（1 = 長期、2 = 短期）を選びます。ばねは荷重の性質で決め、ロングレールは長期、制動・始動などの活荷重は短期です（決定36）。
- FrameWeb のばねの値1は固定支点、0は自由を意味するので、ばねは正で1以外の値が必要です。荷重のない部材行は書きません。部材荷重の強度は FrameWeb が 0.01 に投影します。行のない荷重ケースは FrameWeb が飛ばすので、そのようなケースだけの Combine は落ち、その Pickup は失敗します。Combine の表は Define 50列までです。こうなる入力は公開前にエラーにします。
- **FrameWeb は係数×荷重を丸めずに組み合わせます**。計算書は作用ごとに係数×作用を印字桁に丸めるので、FrameWeb の組合せは計算書の印刷値と作用ごとに最大0.005程度ずれます。外部の解析ソフトとしてこの差を許容します（決定38）。
- **0620 の FrameWeb は Example2 の Define の構成のままです**（列車・衝撃・遠心を線ごとに独立に選ぶ）。そのため上り線の列車と下り線の衝撃の組も選びうるので、FrameWeb の包絡は、同じ線どうしだけを組み合わせる計算書より安全側に出ます（決定39）。FrameWeb の形式には Define 同士の選択を連動させる項目がなく（Define・Combine・Pickup の知らないキーは読込みで拒否されます）、各 Define は独立に包絡されるので、同じ線どうしに限定できません。
- 出力は FrameWebforJS/CS の保存形式のJSONで、FEMPython の解析要求のJSONではありません。`FrameWebforCS.Headless.exe run --input <json> --output-dir <空の絶対パス>` が、保存形式から計算要求への変換・計算・Define/Combine/Pickup までを行います。FEMPython はこの中で使われる計算エンジンで、保存形式を直接は読みません。
- **読込みの確認**（2026-10-18、`scripts/check_frameweb_headless.py`、記録 `tests/fixtures/acceptance/frameweb_headless/record.json`）：`pre/input.json` と `current.json` の 0610・0620（両入力で同じバイト）を FrameWebforCS.Headless（FEMPython）で計算させ、節点・部材・Define・Combine・Pickup の数、荷重ケースごとの反力と書いた荷重の釣合い、0610 の組合せ1（FEMPython 22585.1473、計算書 22585.160、作用ごとの丸めの差は最大0.005）を照合しました。行のない荷重ケース5（低水位の浮力が0）とその Define 5 は FrameWeb が飛ばします。0620 は風荷重の終わる位置（y = 4.7 m）に FEMPython が節点を1つ加えます。読込みを確かめるための計算で、構造解析・照査の結果ではありません。生成する FrameWeb 入力が変わると `tests/acceptance` が失敗するので、確認をやり直します。
- 基礎の剛域は Example2 と同じく、明示した節点・部材に有限の剛性（E = 26,500,000 kN/m²、A = Iz = 1,000）を与えて表します。保存形式の `rigid` 配列は部材端の区間に別の断面を割り当てるだけで、剛体の拘束ではないためです。A・Iz を10倍・100倍にしても柱頭の変位が約0.004 mm 変わるだけで、反力・断面力はほとんど変わりません。
- `Xp` は熱膨張係数です。G・J・Iy の null は2次元への投影で1になります。荷重ケースの `rate` は計算要求に写されず、倍率として効きません（Example2 と同じく1を書きます）。
- FrameWebforCS の画面で保存し直すと、知らないトップレベルのキーは捨てられ、多くの数値が Single 精度に変わります（例：回転ばね 52,218,663 → 52,218,664）。付帯JSONのSHA256による保証は、画面で保存し直したファイルには及びません。別名で保存し、生成したファイルと付帯JSONの組を保管してください。

### JRSNAP（5.2-L03 NDU）

0710 から `post/線路方向.ndu`、0720 から `post/線路直角方向.ndu` を CP932・CRLF で作ります。柱下端の0.010 mの微小部材を M-θ 部材とし、その断面は柱の配筋（方向別の鉄筋配置表）と入力条件から JRSNAP が自動算定します。他の部材は剛域、基礎は 0500 の短期 Ks・Kv と FootInfo（Df・γ2 など）による非線形回転ばねです（CONTEXT.md「JRSNAP入力モデル」）。

- 解析設定（分割数・制限ステップ・目標変位）は入力です（決定40）。ソルバーの数値制御（荷重分割1000、試行回数999、収束判定0.001）は設計条件ではないので、出典つきのプログラムの定数です。
- 上載土はフーチング重心に載荷します。非対称な基礎の斜めの剛部材は、鉛直と水平の2本の剛部材に分けて出力します（決定40）。
- JRSNAP は鉄筋配置表の先頭と末尾の段を引張鉄筋とみなし、面を区別しません。着目方向の主鉄筋がちょうどその段にならない配置（主鉄筋より外側や段のあいだの側面鉄筋）や、自動配置から動かした詳細位置は表せないので、入力エラーにします。
- 部材係数 γb（Vcd・Vsd・Vdd）の説明書の標準値は 1.3・1.1・1.2 で、Example2 の 2.0・1.3・1.8 とは異なります。どちらも補わず、必須の入力です。
- 対象の版は JRSNAP_Input.exe 5.2-L03（FileVersion・ProductVersion 5.2.3.0、AssemblyVersion 5.2.3.1）で、保存のヘッダは `Virsion=5.2.3.S.4`（キーの綴りは JRSNAP のまま）です。Example2 の NDU は 5.1.10 の保存で、5.2-L03 は DataInfo（23→26欄）、SectInfo（12→14欄）、SectSafe（11→12欄、GBVO = 1.3）、FootInfo（12→14欄、KR3 = 20 と未設定値 −3.402823E+38）の末尾に欄を加えます。
- JRSNAP は NDU を先頭から順に読むので、レコードの順序は変えられません。`Tisou=` は TishouNum = 0 でも空のまま必要です（消すと読込みで例外になります）。`TanbuShiji=0,0` は断面のせん断耐力の算定に使う支持条件で、骨組のばねとは関係ありません。
- 固定の設定値の根拠は Example2 の NDU と JRSNAP 5.2-L03 の操作説明書（`.claude/agents/jrsnap-operator/JRSNAP_Ver5.2-L03/JRSNAP_操作説明書.pdf`）です：座標 p.38、M-θ の集約 p.32–33、剛域の初期値 1000 m²・1000 m⁴・25 kN/mm² p.144–145、直接基礎の回転ばね KR2 = 2・最終勾配 1/20 p.155・515、La/d ≥ 2 と M-θ の名前20バイト p.143、件数の上限 p.29、SectConc の第5欄（粗骨材最大寸法）p.90・529。
- 通常の生成は NDU を書くだけで、JRSNAP での読込み・解析はしません。付帯JSONの `app_read_verified` と `analysis_run` は常に false です。
- **実アプリでの受入**（決定4、2026-10-18、`scripts/accept_jrsnap_ndu.py`、記録 `tests/fixtures/acceptance/jrsnap_v52/`）：`current.json`（Example2 の解析設定）の両方向の NDU の複製を、JRSNAP_Input.exe 5.2-L03 の読込み・保存の処理（スキル `jrsnap-input-open-save`、画面は操作しない）で読込み・保存・再保存しました。保存した NDU は全レコードが同じ順序・同じ値で、違いは JRSNAP の数値の書式（`GanmaA=1.2,1,1,1` → `1.20,1.00,1.00,1.00`）だけです。2回目の保存は1回目とバイト単位で同じです。読込み直後に JRSNAP が保持する件数と組合せ（`scripts/jrsnap_state_probe.cs`）も書いたものと一致し、**0720 の2つの組合せ（上り線・下り線）は両方とも読まれます**（`G_intConbNum = 2`）。このため 0720 は1つの NDU のままです（決定40）。解析（解析用データ出力・SNAP の実行）はしていません。生成する NDU が変わると `tests/acceptance` が失敗するので、受入をやり直します。受入は `current.json` で行います。

## Example2 との既知の差

現在の入力（`tests/fixtures/inputs/current.json`。`pre/input.json` も JRSNAP の解析設定のほかは同じ値）で Example2 と比べたとき、設計上残している差です。根拠はそれぞれのテストに書いています。

- **Example2 が丸めない中間値で印刷している箇所（0.01程度）**：WebPier は印刷された値から計算するので、Example2 の隠れた桁による差が残ります。例：08 p.8-4 の RB = 544.93（丸めない 272.4668 × 2）に対し 272.47 × 2.000 = 544.94。07 p.7-8・7-9 の 2851.85・7-11 の 2613.85 に対し 2851.84・2613.84。08 p.8-5 の 428.28 に対し 120.98 + 307.31 = 428.29。09 p.9-5 も同様です（`tests/calc/test_reaction_longitudinal.py`、`test_longitudinal_loads.py`、`test_transverse_loads.py`、`tests/export/test_frameweb_*loads.py`）。
- **シェルター荷重の集約**：WebPier にシェルターの機能はなく、入力はシェルター分を支承の D1・D2・S2 に集約し、風の受風高さは h4（9.433 / 10.767）、直角方向の地震時の桁慣性力は等価重心高 hs = M/H（2.952 / 3.066）に含めています。
  - 風荷重の H は Example2 と一致します（列車ありの起点側 197.00 など）。列車なしの 393.99・217.76 は Example2 の 394.00・217.75 と0.01違います（h4 を3桁に逆算したため）。風荷重の M は、シェルターを鉛直の偶力として扱わず高さに含めるので Example2 と異なります（0620 の合計 M は列車あり 2124.50・列車なし 4248.93、Example2 9-7・9-8 は 1001.33・2002.64）。この差はユーザーが許容しています（`tests/calc/test_reaction_transverse.py`、`test_transverse_horizontal.py`）。
  - 直角方向の地震時の桁慣性力は、起点側 6720.00 × 2.952 = 19837.44（Example2 19838）、終点側 2370.00 × 3.066 = 7266.42（Example2 7267）です。終点側の H は Example2 の 2360 に対し +10 kN（原本の独立反力 640 kN と集約した D1＋S2 = 400＋250 = 650 kN の差）で、線路方向の一致を保つため入力は調整しません。0720 の EQ1 は Example2 11-8 の H = 9080.00・M = 27105.00 に対し H = 9090.00・M = 27103.86 になり、原本の桁本体とシェルター偶力の内訳行は再現しません（`tests/calc/test_seismic_transverse_actions.py`）。
- **はりハンチの重心**：幅と奥行きが直線的に変わる立体の厳密な式 z = ∫z·b·w dz / ∫b·w dz を使い、0.389 m です。Example2 は錐台の式で 0.390 m（相似な断面でだけ厳密）で、0.001 m 違います（決定22、`tests/calc/test_reaction_self_weight.py`）。
- **0610・0620 の D1 の内訳**：0600 のはり重量（直方体＋ハンチ全体、1503.27 kN）を天端に置き、柱の線荷重と重なる H2＋H3 = 2.700 m を控除します。Example2 8-3 ははり 1190.70 と張出しハンチ 104.19 を置いて H2 = 2.00 m だけを控除するので途中の合計は違いますが、天端の N = 8299.53 は一致します（`tests/calc/test_longitudinal_loads.py`）。

品質ゲートは `.claude/check.ps1` の1コマンドです（`& ".claude/check.ps1"`）。全件を coverage の下で実行し（`python -m webpier` などの子プロセスも `pyproject.toml` の `[tool.coverage]` の `patch = ["subprocess"]` で測ります）、層ごとの行・分岐カバレッジを下限と照合します（決定15）。下限は `webpier/core`・`inputs`・`calc`・`export`・`pipeline` が 100%、`reporting` が 95%、`gui` が 85% で、テストの失敗か下限割れで exit 2、ゲートを実行できなければ exit 3 です。結果の JSON の `tools.coverage.packages` に層ごとの値と合否が出ます。

テストは層ごとに `tests/core`・`inputs`・`calc`・`reporting`・`export`・`pipeline`・`gui` にあり、Excel は使いません。`tests/acceptance` は、実アプリでの受入記録（`tests/fixtures/acceptance/`）が今の生成物のものであることを確かめます。実アプリは起動せず、生成物が変われば skip せずに失敗します。

- 期待値は二種類だけです。Example2 の原資料から独立に転記した値（`tests/fixtures/example2/*.json` と転記の注記 `*_notes.md`、柱配筋 `column_rebar_example2.json`、FrameWeb の保存ファイルの写し `frameweb_*.json`）と、実装を使わない手計算（`Decimal`・四捨五入）です。実装の出力から期待値を作りません。実アプリでの受入記録は期待値ではなく、実アプリが読んだ生成物とその読戻しの記録です。
- 入力は `tests/fixtures/inputs/current.json` を基に、変えたい項目だけを書き換えて作ります。
