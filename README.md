# WebPier 鉄道橋脚の荷重計算

`pre/input.json`（schema 2）を読み、0400 照査の前提（柱・梁・フーチングの構造細目）、0500 直接基礎の地盤ばね、0600 上部工反力・橋脚自重、0610 線路方向荷重、0620 直角方向荷重、0710 地震時の線路方向荷重、0720 地震時の線路直角方向荷重を計算し、A4縦・白黒の計算書PDFと結果JSONを作成します。0610・0620 からは FEMPython / FrameWebforCS の入力、0710・0720 からは JRSNAP 5.2-L03 の入力（NDU）も作成し、その NDU を JRSNAP に読ませて描いたデータ確認図と荷重図のページを 0710・0720 の計算書に差し込みます。入力の出力項目（`outputs`）で骨組解析を選べば、0611・0621 でその FrameWeb 入力を FEMPython で骨組解析し、ピックアップ断面力・変位量・反力のファイルも作成します。0611 はさらに、そのピックアップで柱下端の断面照査を Capacita に行わせ、計算書（8.5〜8.10）と Capacita で開ける WDJ も作成します。0612・0622 は同じ骨組解析の支点反力で直接基礎の照査（鉛直支持・水平支持・回転）を行い、計算書（8.11・9.11）を作成します。静的非線形解析を選べば、0711・0721 で両方向の NDU を JRSNAP で静的非線形解析し、解析用データ（.NDT）と解析結果のファイルに加えて、その結果を Aggre-SE（structural-mcp の `Batch`、Docu-SE）で耐震照査するためのプロジェクトXMLも作成します。

計算はPython、計算書の組版は GridLayoutPdf、PDF描画はその ReportLab バックエンド、配筋図は ezdxf です。実行時に Excel や元の xls・PDF は使いません。骨組解析は FEMPython、柱・フーチング・片持ち梁の断面照査は Capacita（RC標準 R5）に任せ、WebPier はそのピックアップを設計応答値として基礎の安定計算に使います（[ADR-0006](docs/adr/0006-frame-analysis-by-fempython.md)）。**寸法・配筋の最適化は対象外**です。

用語は [CONTEXT.md](CONTEXT.md)、原則は [docs/adr/](docs/adr/)、決定事項は [.claude/docs/plans/refactoring-decisions.md](.claude/docs/plans/refactoring-decisions.md) を正とします。

## 実行

Windows専用です。リポジトリのルートで実行します。初回は `uv` がPythonと依存ライブラリを準備します。

```powershell
uv run --project "." --locked python -m webpier                     # 入力の出力項目（outputs）の計算書を作る
uv run --project "." --locked python -m webpier --overwrite         # 既存の成果物を更新する
uv run --project "." --locked python "./run_design.py" --overwrite  # python -m webpier と同じ
```

### 出力項目（`outputs`、決定72、ADR-0011）

入力の `outputs` は13の項目で、どれも `true` か `false` です（全項目が必須、`null` は不可）。項目は、それが使う項目がすべて `true` のときだけ `true` にできます。違反と、全項目が `false` の入力は入力エラーです。コマンド・headless runner・structural-mcp・入力エディタのどれも、この項目だけに従います。

| キー | エディタの表示 | 段階 | 使う項目 |
|---|---|---|---|
| `detailing` | 照査の前提 | 0400 | — |
| `ground_model` | 地盤のモデル化 | 0500 | — |
| `reactions` | 上部工反力及び橋脚自重 | 0600 | — |
| `longitudinal` | 線路方向の計算（地震時以外） | 0610 | `ground_model`・`reactions` |
| `longitudinal_frame_analysis` | 骨組解析も行う | 0611・0612 | `longitudinal` |
| `transverse` | 線路直角方向の計算（地震時以外） | 0620 | `ground_model`・`reactions` |
| `transverse_frame_analysis` | 骨組解析も行う | 0621・0622 | `transverse` |
| `longitudinal_seismic` | 線路方向の計算（地震時） | 0710 | `ground_model`・`reactions` |
| `longitudinal_nonlinear_analysis` | 静的非線形解析も行う | 0711 | `longitudinal_seismic` |
| `transverse_seismic` | 線路直角方向の計算（地震時） | 0720 | `ground_model`・`reactions` |
| `transverse_nonlinear_analysis` | 静的非線形解析も行う | 0721 | `transverse_seismic` |
| `footing` | フーチングの計算 | 0800・0810・0820 | 両方向の `*_frame_analysis` か両方向の `*_nonlinear_analysis`（どちらか一方の組。下の注） |
| `cantilever` | 片持ち梁の計算 | 0900・0910 | 両方向の `*_nonlinear_analysis` |

`footing` は、そろった解析の組の部分だけを作ります（決定110）。両方向の骨組解析だけなら地震時以外の部分（0800 の安全性・使用性の列、0810・0820 の安全性・耐久性・最小鉄筋量及び最大鉄筋量）、両方向の静的非線形解析だけなら地震時の部分（0800 の地震時の列、0810・0820 の復旧性（地震時））、両方なら全部です。0810・0820 の節の番号は出す節だけで詰め、0820 は 0810 の続きです。選ばれていない側の解析は計算しません。

杭基礎（`下部構造.基礎形式` が場所打ち杭・鋼管ソイルセメント杭）では、選べる項目を段ごとに広げます。いま選べるのは `detailing`・`ground_model`・`reactions`・`longitudinal`・`longitudinal_frame_analysis`・`transverse`・`transverse_frame_analysis` と、場所打ち杭だけ `longitudinal_seismic`・`transverse_seismic`（0710・0720、決定93）・`longitudinal_nonlinear_analysis`・`transverse_nonlinear_analysis`（0711・0721、決定94）・`footing`（0800・0810・0820、決定96）です（ほかは `outputs.<項目>` の入力エラー）。`ground_model` は 0500 の杭基礎用（下の「杭基礎の 0500」）で、SOIL-JR を動かす JRSNAP の runner が要ります。`longitudinal`・`transverse` は杭を入れた骨組（下の「杭基礎の 0610・0620」）で、SOIL-JR の runner と FEMPython の runner が要ります。直接基礎の入力は `杭基礎` と `鉄筋.杭` を使わないので、その項目（どちらも丸ごとでも）はなくてかまいません。書いてある値は形と桁を確かめます（決定107）。

項目と段階の対応は `webpier/inputs/outputs.py`（項目と使う項目）と `webpier/pipeline/stages.py` の `OUTPUT_STAGES` が持ちます。地震時の項目は地震時以外の項目を使いません（決定78）。0710・0720 は、使う固定死荷重・付加死荷重・浮力（平水位）・雪荷重（2年確率）を 0610・0620 と同じ計算で自分の骨組に求めるので、0610・0620 を選ばずに作れ、FEMPython の runner も要りません。

### 杭基礎の 0500（決定80・83・85、ADR-0013）

杭基礎の 0500 は、WebPier が地盤ばねや支持力を計算せず、SOIL-JR 5.2-L03 に計算させます。段階の登録表（`stages.py`）で、直接基礎の 0500（`0500_直接基礎`）の `foundations` に杭基礎の 0500（`0500_杭基礎`）を持ち、入力を読んだ直後に基礎形式で引き当てます（`Registry.for_foundation`）。

1. 入力から SOIL-JR の入力の値を導きます（`webpier/calc/pile_ground.py`）。杭頭より上の地盤は、フーチング底面の深さ Df（H6＋H5＋min(df1, df2)）までの層を、水位より上・下の厚さで加重した湿潤・水中単位体積重量の1行にします。杭の区間（フーチング底面から杭長）は、地盤の層をその深さで切った行にします（最後の層は下に続く。Ex＝Ed、ρgE＝γgE＝1。砂質土・砂礫は N値・φd、粘性土は N値・c が要る。砂質土と粘性土の互層は入力エラー）。杭の断面（場所打ち杭は A＝πD²/4、I＝πD⁴/64 と Ec〔f'ck の表の補間〕、鋼管ソイルセメント杭は A＝πDsc²/4、I＝π{(Dsp−2c)⁴−(Dsp−2t)⁴}/64 と Es＝200 kN/mm²）と、列ごとの本数・距離を配置から求めます。
2. .sdt を書きます（`webpier/export/soiljr/`。SOIL-JR 5.2.3 が保存する形、CP932・CRLF）。地盤抵抗係数は未入力の目印で書き、SOIL-JR に求めさせます。
3. JRSNAP の runner の `soil` 命令（JRSNAPHeadless、環境変数 `STRUCTURAL_MCP_JRSNAP_RUNNER`）で SOIL-JR を動かします。0500（杭基礎）を含む生成は、runner がないと止まります。
4. 成果物：`output/0500_杭基礎.pdf`（SOIL-JR の帳票を、印刷のメニューと同じ全項目、runner が出したバイト列のまま。WebPier は頁も見出しも足さず、方眼Excelもありません。印刷日が入るので生成のたびに変わります）、`output/0500_杭基礎.json`、`post/杭基礎.sdt`・`杭基礎.sdr`・`杭基礎.sdc`（液状化を考慮する入力、つまり杭の区間の層の De が 1 未満のときは `杭基礎(液状化時用).sdr`・`.sdc` も）と、それぞれの付帯JSON（`soil_jr`：runner、SOIL-JR の版、.sdt の SHA-256、警告。`engineering_status` は `not_evaluated`）。.sdr・.sdc は SOIL-JR が返したバイト列のままで、同じ入力から毎回同じです。
5. 結果JSON（`result`）：導いた値（`ground`：杭頭より上の地盤、杭の区間の行、杭の断面、杭の列、液状化の有無）、渡した .sdt の SHA-256、.sdr の表（`sdr`・`liquefied_sdr`。設計鉛直支持力・設計引き抜き抵抗力・水平変位の設計限界値 δL・回転角の設計限界値 θL を方向・条件ごとの表として）。.sdr の見出し（杭種・杭長・列数・本数）が渡した入力と違えば生成を止めます。0612・0622 と Aggre-SE の杭基礎の制限値は、この表と .sdc から取ります（ロードマップ P5 以降）。

### 列車の配置（決定102）

線路方向の地震時以外の照査では、列車荷重を ① 両側の桁、② 起点側の桁のみ、③ 終点側の桁のみ の3通りに載せます（【橋りょう編 5.4.3】、Example橋脚4 I-40 表7.1.2）。片側の桁のみの配置では、もう一方の桁に列車を載せません。車両によらず、P-16 にも適用します。

1. 0600：3通りの移動荷重の支点反力、配置ごとの橋脚く体の衝撃の比（L はその配置の RB＋RC）と列車荷重・衝撃荷重の表、桁ごとの制動荷重と始動荷重、列車か制動を含む5つの支承の水平荷重の組合せを、配置ごとに求めて印刷します。複線の組合せでも、制動荷重は1軌道分です。
2. 0610：列車荷重（単線・複線）、衝撃荷重（単線・複線）、列車か制動を含む支承の水平荷重の基本ケースは、配置ごとに3つ続けて作ります（38の基本ケース）。16の組合せのうち列車を含む11は、①②③の3つを続けて並べます（38の組合せ）。抽出ケースは、その組合せの種類の全配置から拾います。FrameWeb の荷重ケースの記号は見本と同じく `L1-1`・`L1-2`・`L1-3` のように配置の番号を付け、組合せの名前には配置を付けます。
3. 0620（線路直角方向）・地震時（0710・0720）・0900 は ① だけです。

### 杭基礎の 0610・0620（決定88、ADR-0013）

杭基礎の 0610・0620 は、フーチング底面のばねの代わりに杭をつないだ骨組です（Example橋脚4 III-1、図 1.2.3）。

1. 骨組：フーチングは剛で、底面に水平の剛な部材を通し、杭列ごとに1本の杭の部材を杭頭で剛結します（軸は杭径の中心）。杭の断面は杭頭の1つで全長を表し、段落しは入れません（鋼管は腐食代を除いた有効肉厚の鋼管だけ、場所打ち杭は円形断面で、`webpier/calc/pile_frame.py`）。杭列の位置は入力の `杭基礎.配置`、杭列の A・I は1本当りの値に列の本数（奥行き本数）を掛けた値です。柱・フーチングの上の部分は直接基礎の骨組と同じです。
2. ばね：SOIL-JR の解析連携データ .sdc の「解析用地盤ばね値」を、そのまま使います（`webpier/export/soiljr/sdc.py` が読み、WebPier は地盤を求め直しません）。杭周面の水平ばねは層ごとの長期と短期（線形）、鉛直せん断ばねは**押込み側**の表の長期と短期（使用性・安全性）で、層の厚さごとの区間の分布ばね（部材の `fix_member`、杭頭から）にします。最小根入れの区間（押込み側で鉛直せん断ばねがない部分）は、最下層だけ引抜き側の鉛直せん断ばねを使い（見本の表 III-21、決定89）、ほかの層の押込み側に鉛直せん断ばねがない部分は水平ばねだけの区間に分けます。杭先端は鉛直ばね（と、SOIL-JR が出すときは水平・回転ばね）の節点ばねです。FrameWeb 入力は `fix_node` と `fix_member` の1番が長期、2番が短期で、荷重ケースがその組を選びます。

### structural-mcp から使う（headless runner、決定61）

structural-mcp（MCP の `webpier_get_input_schema`・`webpier_get_contract`・`webpier_validate`・`webpier_generate`）は、repo のルートの `run_headless.py` を venv の python で起動します。直接呼ぶ場合も同じです。

```powershell
.venv\Scripts\python.exe -X utf8 .\run_headless.py run --input pre\input.json --output-dir <空のフォルダー>
.venv\Scripts\python.exe -X utf8 .\run_headless.py validate --input pre\input.json
.venv\Scripts\python.exe -X utf8 .\run_headless.py contract
.venv\Scripts\python.exe -X utf8 .\run_headless.py schema
```

- stdout は JSON 1つ（protocol v1 の envelope、`engine: "webpier"`）。`run` は `--output-dir` の下に `output/`・`post/`・`export/` を CLI と同じ配置・同じバイトで書き、`artifacts` に全ファイルの相対パス・SHA-256・サイズを返します（JRSNAP の結果フォルダーは中のファイルを1つずつ）。
- 作る段階は入力の出力項目だけで決まり（決定72）、`summary.outputs` に選んだ項目を返します。`--stage` などの選択の引数はありません（付ければ `INVALID_ARGUMENT`）。
- runner は**環境変数だけ**から読みます（`.env` は読みません）。選んだ出力項目が要る runner がなければ何も書かずに `RUNNER_UNAVAILABLE` で終わります。
- 終了コードは CLI と同じ（0・2・3）。失敗の種類は `errors[0].code`（`INVALID_ARGUMENT`・`INPUT_ERROR`（入力のパス付き）・`ADDIN_ERROR`（下の「荷重モデルのアドイン」）・`RUNNER_UNAVAILABLE`・`ENGINE_FAILED`・`GENERATION_FAILED`・`IO_ERROR`・`RECOVERY_REQUIRED`）。
- `engineeringStatus` は段階ごと（0400・0612・0622 は ok／not_ok、ほかは not_evaluated）と全体（not_ok が1つでもあれば not_ok、判定した段階がすべて ok なら ok）。実行の成否（`ok`）とは別です。
- `validate` は runner を呼ばずに決まる範囲（解析・計算・外部出力・Aggre-SE のプロジェクトの入力）を確かめます。`contract` は段階（依存と出力項目）と、出力項目ごとの段階・使う項目・選ぶと要る runner（使う項目の分も含む）・公開するファイル（`outputs`。各項目の `pileFoundation` は杭基礎で作るときの同じ内容：`supported`〔杭基礎で選べるか〕・`foundations`〔作れる杭基礎の基礎形式〕・`runners`・`files`・`conditionalFiles`〔液状化を考慮する入力だけに出るファイル〕。決定85）、`schema` は入力の JSON Schema（項目表から。必須と項目間の規則は `validate` が正）。

### 荷重モデルのアドイン（`--addin`、決定70、ADR-0010）

死荷重以外の支承作用と作用の組合せは、荷重モデルとして差し替えられます（CONTEXT.md の 荷重モデル・支承作用）。案件の荷重モデルは案件の repo に置くアドインで、`--addin <フォルダー>` で読み込みます。付けなければ、いままでどおり列車荷重で計算します（成果物は1バイトも変わりません）。

```powershell
uv run --project "." --locked python -m webpier --addin <アドインのフォルダー> --overwrite
.venv\Scripts\python.exe -X utf8 .\run_headless.py run --input pre\input.json --output-dir <空のフォルダー> --addin <アドインのフォルダー>
.venv\Scripts\python.exe -X utf8 .\run_headless.py contract --addin <アドインのフォルダー>   # validate・schema も
```

- アドインのフォルダーには `webpier-addin.toml`（`name`・`version`・`contract`（約束の版、いまは 1）・`entry = "モジュール:関数"`）と、そのモジュール（`<モジュール>.py` かパッケージ）を置きます。関数は引数なしで、`calculate(context) -> LoadModelResult` を持つものを返します。アドインが import してよいのは `webpier.loadmodel` だけです。見本は `tests/fixtures/addin/minimal/`。
- 約束（`webpier/loadmodel/`）：基本ケースごと・支承ごと（起点側・終点側 × 支承の枠 1〜10）の支承作用（鉛直力、線路方向・直角方向の水平力とその作用高さ。力は小数2桁、高さは3桁の Decimal）、基本ケースのばね（長期・短期）と地震時の固定・増分・限定増分と向き、骨組（0610・0620）の組合せと8つの抽出ケースへの割り当て、地震時（0710・0720）の組合せ（逆向は `reverse=True`。アプリが照査パターン（ρm・αf）の4つに展開する。決定76）、片持ち梁（0900）の組合せと Capacita の力の表の8行への割り当て（係数に最大応答震度 `MaxResponse` も可）、計算書に差し込む根拠の節（段落と文字の表）、来歴の辞書。組合せからは、アプリの基本ケース `D1`・`D2`・`WP_HIGH`・`WP_NORMAL`・`WP_LOW`（骨組）、`PIER_WIND_<n>`（0620 の躯体の風、`pier_wind_pressures` の n 番目の風圧）、`EQ2`（地震時の橋脚自重の慣性力）を id で参照します。
- アプリは結果を受け取るときに検査し（`loadmodel.validate`）、違反は `アドイン:<場所>` の入力エラーにします（id の一意、参照先、空き支承枠、印字桁、符号 −1 は鉛直力0のケースだけ、地震時のケースは NDU の15まで、ほか）。
- 0600 は死荷重・自重だけ、0610・0620・0710・0720・0900 は荷重モデルの結果から作り、それ以外の段階は同じものを使います（`pipeline.stages.stages_for`）。支承作用は M = N × アーム ＋ H × y で支承の座（桁受けに載る桁は桁受け天端、ほかははり天端。決定81）ごとに集めた橋脚天端の等価作用にします（0720 の水平力はその側の桁の節点に載せます）。組合せのない抽出ケースは荷重0のケース（`ZERO`、FrameWeb には ty = 0 の1行）で断面力0として通し、計算書に「該当する組合せなし（断面力0）」と印字します。Vd＝0 で割る照査（基礎の照査、フーチング）は抽出ケースの名前を入れた入力エラーです。0720 の制御節点は、増分の地震時ケースの直角方向の支承作用を起点側・終点側ごとに合計した値の大きい側の桁の節点です（決定81）。0710・0720 の計算書には荷重モデルの根拠の節を出しません（決定81）。
- アドインをつないだとき、入力の荷重モデルの項目（`列車`、各側の `衝撃係数_単線終局`・`曲線半径`・`列車速度`・`遠心作用方向`、支点・支承の雪荷重と `列車分担`）は読みません（検査も印字もしない。あってもなくてもよい）。入力エディタはアドインに対応しません（エディタの「計算・印刷」は列車荷重で計算します）。
- 来歴：アドインが宣言した名前・版・約束の版と、アドインが返した来歴の辞書を、解釈せずに全結果 JSON・全付帯 JSON と runner の `summary.addin` に `addin` として写します。アドインのファイルのハッシュは取らず、アドインの入力も読みません（アドインの責任）。
- 失敗：宣言がない・約束の版が違う・import や `calculate` が例外を出すと `ADDIN_ERROR`（終了コード 2）。アドインが自分の入力の誤りを `LoadModelInputError` で知らせると `INPUT_ERROR` です。
- `schema --addin` は荷重モデルの項目に `x-webpier-load-model: true` を付け、どの値でもよいとします。

VS Code では **F5**（「橋脚 入力データ編集 (Tkinter)」、起動先 `edit_input.py`）でも起動できます。左の一覧から「01 下部構造」「02 上部構造」「03 上部工反力」「04 地盤データ」「05 杭基礎」「06 鉄筋」「07 JRSNAPの設定」「08 計算・印刷」を選びます。「杭基礎」は、基礎形式が杭基礎のときの杭の諸元と配置（列の位置・抜く杭は行を足して入力）のページで、直接基礎では使わない旨だけを示します。表は tksheet で、範囲選択・コピー・貼り付け・元に戻すが使えます。

- 数値は入力した時点で印字桁に丸め、入力JSONには丸めた値を保存します。桁・単位・符号・選択肢は入力の項目表（`webpier/inputs/fields.py`）から取り、計算と同じ規則で検査します。
- 空欄は `null` として保存できます。計算に要る空欄と、入力できない値は赤で示します。入力できない文字が残っているあいだは保存しません。
- 値は補いません。B9 は「B7と同じ」、A・D支点の合計は「B/Cと同じ」ボタンで、その時点の値を明示的な入力として書き込みます。空き支承枠に入力を始めたときの他の項目や、新しく追加した鉄筋の行・鉄筋は、選択肢を含めてすべて空欄で始まります。
- 「入力チェック」は全段階の入力条件を確かめ、最初の入力エラーをパス付きで表示します。
- 保存は、開いた後に他から変更されたファイルを上書きしません。置き換える前のバイトを同じフォルダの `input.json.<日時>.bak` に残します。
- 「計算・印刷」には出力項目（[上記](#出力項目outputs決定72adr-0011)）の13のチェックを「項目名（段階の番号）」で並べ、「骨組解析も行う」「静的非線形解析も行う」はその方向の項目の下に字下げして置きます。チェックは入力JSONの `outputs` に書くので、付け外しも入力の変更です（表示中のPDFは今回の結果ではなくなります）。使う項目にチェックがないうちは灰色で選べず、項目のチェックを外すと、それを使う項目のチェックも外れます。`outputs` のない入力は、最初のクリックで13項目すべてを書きます（ほかは `false`）。
- 「保存して計算・PDF出力」は、入力を保存し、`python -m webpier --overwrite` を子プロセスで実行します（作る計算書は保存した入力の出力項目で決まります）。静的非線形解析は数分かかり、JRSNAP の画面が出ます。出力先は `./output` と `./post` です。結果JSONと付帯JSONが保存した入力のSHA256を指し、付帯JSONが同じ世代の全ファイルを列挙していることを確かめてから、PDFプレビューを開きます。後から入力や出力ファイルが変わると、表示中のPDFを「今回の結果ではない」と示します。
- 「JRSNAPの設定」の画面に、JRSNAP の解析設定（方向ごとの項目、[入力](#入力schema-2)を参照）の欄があります。線路方向の計算（地震時）を選ぶと線路方向の、線路直角方向の計算（地震時）を選ぶと線路直角方向の全項目が必要です。静的非線形解析の耐震照査の入力に使う `耐震設計条件`（地域別・地盤区分）は「地盤データ」のページにあります。

鉄筋の画面は、部材ごとに配筋を入力します（決定68）。柱は、主鉄筋のタブに共通の帯（材質・コンクリート・Dmax・純かぶり・外側の帯鉄筋の径）と方向別のカード（1段目の径・本数・芯かぶりの決め方・並べ方と、その並べ方が使う値だけ、2段目以降の本数とあき）を、帯鉄筋のタブに方向別の範囲のカードを置きます。説明の図や式は (?) で開きます。柱の断面図と方向別の鉄筋配置表は「断面図・配置表」のウィンドウ（開いたまま入力でき、入力のたびに描き直す）で見ます。柱の配置と方向別の鉄筋配置表は `webpier/calc/column_rebar.py` が計算し、エディタとウィンドウは表示するだけです。方向別の鉄筋配置表は、その方向の計算上の断面です（決定111）。ウィンドウの配置表で、主鉄筋の入力から作った表を出発点に、行の芯位置・径・本数を直し、行を足し（選んだ行の写しを下に）・消し・上下に入れ替え、引張鉄筋の段数 N を変えられます（配置表の手直し、`custom_tables`）。引張鉄筋は表に書いた順の上から・下から N 行です。手直しした表は「入力から作り直す」で戻せ、その方向の主鉄筋の欄を変えたときも作り直されます。表が成り立たなくなる変更は受け付けず、2つの表で径ごとの本数が違えば警告します（計算は止めません）。梁・フーチングは、項目表のパスを並べた暫定の画面で入力し、外形だけを描きます。梁の側面筋は「側面筋なしにする／入れる」で切り替えます。柱では粗骨材の最大寸法と、グループ「断面照査の条件」（`柱の断面照査`）も入力します。

## 入力（schema 2）

`pre/input.json` は `schema_version: 2` です。parser（`webpier/inputs/parse.py`）は入力を一度だけ検査し、各段階はその結果を共有します。

- **知らないキーは入力エラー**です。旧形式の読み替えはしません。
- **値を補いません。** 計算に要る値が空欄（`null`）なら入力エラーです。`0` は数値です。全項目が空欄の支承枠だけは「空き支承枠」（CONTEXT.md）として除外し、L3・L4 は空欄（2線まで、決定23）とします。
- **選択肢はプログラムが持ちます**（`webpier/inputs/choices.py`）。入力JSONには選んだ値だけを保存し、一覧にない値は入力エラーです。車両名は `EA-17` と `P-16` で、軸配置・軸重・後続の荷重・車両横荷重・制動と始動・地震時の列車荷重は車両名で決まります（決定101、`webpier/calc/vehicles.py`。EA-17 は E-17 と A-17 の不利な方、制動は列車荷重の 25 %、始動は動輪軸重の 25 %。P-16 の値は Example橋脚2 の入力から）。`上部構造.列車` に入力するのは車両名・編成数（P-16 だけ。EA-17 は空欄）・車両高・荷重修正係数です。土質区分は「砂質土」「砂礫」「粘性土」「砂質土と粘性土の互層」、基礎形式は「直接基礎」「場所打ち杭」「鋼管ソイルセメント杭」、場所打ち杭の施工条件は「自然泥水」「安定液使用」、杭の配置の形式は「格子」「千鳥」、鉄筋の材質は SD295・SD345・SD390・SD490 です。
- **派生値は入力にしません。** 排除した土の単位体積重量（フーチング高さの範囲の層の湿潤の平均）、B・C支点の合計は計算器が求めて印刷します。表層の層厚は空欄なら Df（H6＋H5＋min(df1, df2)）から下の層の層厚を引いた残りです（決定64）。支承位置 f は両側とも入力します。
- **空欄を 0 とする値**：雪荷重（雪荷重なし、決定62）と支持層の粘着力 c（決定63。決定84 で一軸圧縮強度 qu を c に替えた）。ほかの空欄は補わず入力エラーです（決定5）。地盤の層の `De`（液状化時の低減係数）の空欄は「その層は液状化しない」（1）という入力です（決定80）。地盤の層の `せん断弾性波速度_Vs`（m/s、整数）は省略できるキーで、地盤変位を考慮する入力（杭基礎で地盤区分 G3〜G5）の 0710・0720 だけが基盤面より上の層に要ります（決定97）。
- **入力値は印字桁に丸めてから入力します。** 印字桁より細かい値は黙って丸めず、入力エラーにします。桁は入力票（`.claude/docs/Example橋脚/pre/input-*.pdf`）に合わせています。

## 計算の原則

- **元Excelの誤りは再現しません**（ADR-0001）。WebPier は元Excel（0500〜0720のxlsと転記VBA）を基にしていますが、正規の計算は工学的に正しい式を使います。元式を意図的に残す箇所は、下の互換一覧に理由とともに書いたものだけです。
- **物理量で計算します**（ADR-0002）。元Excelのセル番地、セルの再生、元Excelから採取した照合値は使いません。期待値は Example2 の原資料から独立に転記した値と、実装を使わない手計算だけです。
- **印字桁で計算します**（ADR-0003）。計算書に印刷する値は内部でも印字桁に丸め、後続の計算はその丸めた値を使います。合計・積は印刷された部分の値から求め（0.125 の3行は各 0.13、合計 0.39）、段階間の引継ぎも前段の計算書に印刷された値で行います。印刷しない中間値は作りません。例外は移動荷重の載荷位置の探索で、探索の内部は丸めず、採用した結果を印字桁に丸めて印刷します。丸めは四捨五入（0.5は絶対値の大きい側）だけで、VBA の Single 精度、Excel の ROUND、偶数丸めは使いません。印字桁は計算器（`webpier/calc`）が値ごとに持ち、帳票は丸め直しません。
- **欠けた値を補いません**（決定5）。計算中に成立しない条件（0除算、表の範囲外など）も入力エラーにします。例：コンクリートのヤング係数 Ec は f'ck 18〜80 N/mm² の表の線形補間だけで、範囲外は入力エラー（決定25）。複線の衝撃低減 1 − L/200 は L ≥ 200 m を入力エラー（決定13）。

### 互換一覧

元Excelの式を意図的にそのまま再現する箇所（**元式の互換動作**、CONTEXT.md）の一覧です。元Excelを意図して再現する箇所は、必ずここに理由とともに書きます（ADR-0001）。ここにない元Excelとの差は、すべて誤りとして直したものです。

いまは**ありません**。以前の4点のうち、可動支承の水平力の下限 μ·T/n は正しい設計式として本文の規則にし（決定11）、残る3点（柱下端の集計の桁受けを重量で集計、直角方向のモーメントに桁受けを含める、上載土の xL に線路方向の重心を使う）は元Excelの誤りとして直しました（決定20）。

## 構成

### 層別パッケージ（ADR-0004）

```
webpier/
  core/       Printed（印字桁つきの値）、厳密なJSON読込み、エラー、ハッシュ
  inputs/     schema 2 の解析と検証。項目表 fields.py、選択肢 choices.py
  loadmodel/  荷重モデルの約束（アドインが import してよい唯一のパッケージ）と結果の検査（決定70）
  calc/       段階の計算（foundation, reaction, longitudinal, transverse, seismic_*）と共通の骨組・移動荷重。
              generic/ は荷重モデルの 0610・0620・0710・0720・0900、bearing_actions は支承作用から橋脚天端の等価作用
  reporting/  GridLayoutPdf による計算書（stages/ に段階ごとの組版）
  export/     frameweb/（FEMPython・FrameWebforCS）、jrsnap/（JRSNAP 5.2-L03 NDU）、aggrese/（Aggre-SE のプロジェクトXML）、
              capacita/（Capacita の WDJ）、drawing/（ezdxf の配筋図。DXF と図ごとの PDF・PNG）
  pipeline/   段階の登録表、生成、公開、CLI（python -m webpier）
  gui/        入力エディタ（python -m webpier.gui）
```

依存は `core ← inputs ← loadmodel ← calc ← reporting / export ← pipeline ← gui` の向きだけです（loadmodel は core だけに依存し、モジュールを名前で import する importlib は pipeline だけが使います）。`tests/test_layer_boundaries.py` が強制し、calc・inputs・core は描画や Tk のライブラリも import しません。計算は帳票に依存しません。

### 段階の登録表

段階の依存・計算・帳票・成果物・外部出力は `webpier/pipeline/stages.py` の `StageSpec` の表1か所に定義します。生成・成果物の一覧はすべてこの表から作るので、段階や外部出力の追加は表の1項目です。`calculate` と `render` には宣言した依存段階の結果だけを渡すので、宣言していない依存は動かずに失敗します。計算書のない段階（`render` なし）、依存段階の FrameWeb 入力の骨組解析（`frame_analysis`）、依存段階の NDU の静的非線形解析（`nonlinear_analysis`。返ったファイルを1つのフォルダーで公開する）も表の項目で表します。各段階は1つの出力項目に属し（`Registry.outputs`、既定は `OUTPUT_STAGES`）、登録表は、段階が自分の項目とその項目が使う項目の段階だけを読むことを確かめます（決定72）。そのため、選んだ項目の段階が生成で計算する段階のすべてです。

### 生成と一括公開

1. 入力を一度だけバイト列で読み、厳密に解析します（重複キー・NaN・Infinity は入力エラー）。そのSHA256を全ての結果JSONと付帯JSONに記録します。
2. 入力の出力項目で段階を選び（決定72）、出力先をすべて検査してから計算を始めます。同名のディレクトリやシンボリックリンク、入力と同じパスの出力は拒否します。
3. 選択した段階をすべて計算してから描画します。保存済みの結果JSONは読みません。荷重図のある段階（0610・0620）は、ステージングした FrameWeb 入力を FEMPython の runner に描かせ、そのページを計算書に差し込みます。データ確認図と荷重図のある段階（0710・0720）は、同じ生成で組み立てた NDU を JRSNAP の runner に描かせ（データ確認図と荷重図を1回の呼び出しで）、同じく差し込みます。骨組解析の段階（0611・0612・0621・0622）は、同じ生成で組み立てた FrameWeb 入力を runner に解析させ（荷重図とは別の呼び出し。同じ入力は1回だけ）、計算書を描く前に結果を確かめます。0612・0622 はその反力で基礎の照査を仕上げてから描きます。0611 は続けて、その PIK と WebPier が組み立てた WDJ を Capacita の runner に渡し、返った計算書の節のページを計算書に差し込みます。静的非線形解析の段階（0711・0721）も同じく、同じ生成で組み立てた NDU を JRSNAP の runner に解析させます。runner は計算を始める前に探します。
4. 計算書・結果JSON・外部ソフト向け入力・付帯JSON・JRSNAP のフォルダーを各出力先の横でステージングし、`webpier/pipeline/publication.py` がまとめて公開します。旧ファイル（旧フォルダー）を同じファイルシステム内に退避して置き換え、公開した実バイト・入力・実装の同一性を最後に確かめます。フォルダーの実バイトは、中の全ファイルの SHA256 で確かめます。失敗すれば旧ファイルをすべて戻し、その実行で新しく作ったファイルは消します。複数ファイルがOS上で一瞬に切り替わる仕組みではありません。
5. 強制終了や復元の失敗では、出力先ごとの `.webpier-*` に `publication-pending`・`publication-journal.json` と退避ファイルを残し、次の実行はそれを見つけて止まります。journal の各 `destination`・`backup`・`had_original` を照合して旧成果物を戻すか、一式を別の場所へ保全してから再実行してください。

結果JSON（`output/<段階>.json`）は `schema_version`・`stage`・`input`（ファイル名とSHA256）・`implementation_sha256`・`result` を持ちます。付帯JSON（`post/*.provenance.json`）は、その外部入力のファイル名とSHA256、入力のSHA256、実装のSHA256、選択した段階、同じ世代の全成果物（役割・出力先・ファイル名・SHA256）を記録します。FrameWeb 入力の付帯JSONには、それを描いて計算書に差し込んだ runner の版（`load_diagram.engine_version`）も記録します。NDU の付帯JSONには、データ確認図と荷重図を描いた runner の版と報告（`jrsnap_figures`：差し込んだ計算書 `report`、`engine`・`engine_version`、データ確認図の組合せと図 `data_check`、荷重図のケースと組合せ `load_diagram`、`runner_summary`）を記録します。骨組解析のファイル（`*.pik`・`*_ピックアップ変位量.csv`・`*_ピックアップ反力.csv`）の付帯JSONには、`frame_analysis` に runner の版（`engine_version`）と、解析した FrameWeb 入力の段階・種類・ファイル名・SHA256（`frameweb`）と、そのファイルを使った選択段階（`stages`）を記録します。`線路方向.wdj` の付帯JSONには、`section_check` に Capacita の runner の版、`engineering_status: not_evaluated`、取り込んだ PIK（段階・種類・ファイル名・SHA256）と WebPier が渡した WDJ の SHA256（`wdj_given`）を記録します。`frame_analysis.frameweb.sha256` が、解析結果とその FrameWeb 入力を結び付けます。実装のSHA256は、`webpier` のソースと、インストール済みの GridLayoutPdf・ReportLab・Pillow・pypdf・ezdxf・fontTools・PyMuPDF（配筋図を描いて PDF にする。決定73）・書体ファイルのバイトから求めます（`webpier/pipeline/runtime.py`）。生成中にこれらが変わると公開しません。FEMPython・JRSNAP・Capacita の runner はここに含めません（その出力はそれぞれの責務、決定44・46・47・48）。JRSNAP のフォルダーの付帯JSONは上の「0711・0721」の段落のとおりで、`nonlinear_analysis.ndu.sha256` が解析結果とその NDU を結び付けます。

PDFは作成日時を含まないので、同じ入力・書体・ライブラリからは毎回同じバイトになります。例外は 0610・0620 に差し込む FEMPython の荷重図のページと、0710・0720 に差し込む JRSNAP のデータ確認図と荷重図のページ（ヘッダーに印刷日が入るので、日ごとにバイトが変わります）で、その中身はそれぞれの責務として毎回同じバイトになることを求めません。計算書にはページ番号を印刷しません（体裁の見本どおり）。配筋図の DXF と図ごとの PDF・PNG（`webpier/export/drawing`）も同じ入力から同じバイト列です（ezdxf の CLASSES 節の並びを名前順に固定し、PDF に /ID を書かない）。

## 計算書

計算書はA4縦・白黒で、GridLayoutPdf の共通グリッド（0.2.0 で導入。いまの lock は v0.3.0。16.08×15.48pt のマス、30列×47行）に組みます。字下げ・等号・表の列幅と行高はマスの数で決まり、構成・文言・式の書き方は `.claude/docs/Example橋脚/output` に合わせます。数値・式・ケースは現在の入力から計算します。計算内容の見本は `.claude/docs/Example橋脚2` です。式・表・図のまとまりを保って改ページするので、ページ数は内容に応じて変わります。文字の縮小や伸縮で固定ページ数に収めることはしません。体裁の契約は [.claude/docs/reporting-style.md](.claude/docs/reporting-style.md) にあります。

WebPier が組む頁は、同じものを方眼Excel `export/<段階>.xlsx`（1冊1シート。セルが方眼のマスで、文字・式の項・表の罫線がセルに入る）にも書きます。他のプログラムの頁（FEMPython の荷重図、Capacita・JRSNAP の頁）は入りません。0711・0721 は Aggre-SE の帳票そのものなので、方眼Excel はありません。出し先は `--export-dir`（既定は出力先と並ぶ `export`）。方眼Excel は GridLayoutPdf の strict で書き、セルに置けない部分が1つでもあれば、何も公開せずに止まります。

各帳票の内容は Example2 の対応する計算書に合わせています（0400: 06 照査の前提（文言・式・表は `Example橋脚/output` の 0400）、0500: 04 地盤のモデル化、0600: 05・07、0610: 08、0620: 09、0710: 10、0720: 11）。

- 0500 は地盤ばね（kv・Kv・ks・Ks・Kr、長期・短期、2方向）と支持力係数（解説表13.2.2.3-2、表の中間は線形補間、42度以上は Nγ=150・Nq=85）を計算し、土質区分の係数・指数を印刷します。平坦な土被りでは、JRSNAP に渡す有効根入れ深さ Df と平均有効単位重量 γ2 = ((Df − hw2) × γwet + hw2 × γsub) / Df も印刷します（CONTEXT.md）。Df の範囲に複数の層があるときは、層ごとの水位より上・下の厚さで加重平均した γ2 = Σ(hi × γi) / Df です（支持層より上の層は層厚を入力し、支持層は Df の残り。決定64）。

## 外部ソフト向けの入力

### FrameWeb（FEMPython / FrameWebforCS）

0610 から `post/線路方向.json`、0620 から `post/線路直角方向.json` を作ります。形式は Example2 の FrameWeb 保存ファイル（`.claude/docs/Example橋脚2/08_線路/frameWebForJS.json` など）に合わせています。規則の詳細は `webpier/export/frameweb/` の各モジュールに書いています。

- **座標は現行の FrameWeb 形式（y は下向き）です**（決定44）。Example2 は旧形式（y 上向き）で保存されていますが、FEMPython（FrameWebforCS/Headless・FramePrintPDF）はどの保存ファイルも現行形式として扱うので、旧形式のままでは荷重図が上下逆に描かれます。節点の y、節点荷重の ty・rz、部材荷重の gy の符号を反転して書きます（tx・gx はそのまま）。橋脚を上下に鏡に映しただけなので解析結果は同等です（組合せ1の上向きの鉛直反力は反転の前後とも 22585.1473）。`ver` は書かないので、FrameWebforJS（ブラウザ版）で開くと旧形式とみなされてもう一度反転し、上下逆になります。
- 荷重ケースごとに地盤ばねの組（1 = 長期、2 = 短期）を選びます。ばねは荷重の性質で決め、ロングレールは長期、制動・始動などの活荷重は短期です（決定36）。
- FrameWeb のばねの値1は固定支点、0は自由を意味するので、ばねは正で1以外の値が必要です。荷重のない部材行は書きません。部材荷重の強度は FrameWeb が 0.01 に投影します。行のない荷重ケースは FrameWeb が飛ばすので、そのようなケースだけの Combine は落ち、その Pickup は失敗します。Combine の表は Define 50列までです。こうなる入力は公開前にエラーにします。
- **FrameWeb は係数×荷重を丸めずに組み合わせます**。計算書は作用ごとに係数×作用を印字桁に丸めるので、FrameWeb の組合せは計算書の印刷値と作用ごとに最大0.005程度ずれます。外部の解析ソフトとしてこの差を許容します（決定38）。
- **0620 の FrameWeb は Example2 の Define の構成のままです**（列車・衝撃・遠心を線ごとに独立に選ぶ）。そのため上り線の列車と下り線の衝撃の組も選びうるので、FrameWeb の包絡は、同じ線どうしだけを組み合わせる計算書より安全側に出ます（決定39）。FrameWeb の形式には Define 同士の選択を連動させる項目がなく（Define・Combine・Pickup の知らないキーは読込みで拒否されます）、各 Define は独立に包絡されるので、同じ線どうしに限定できません。
- 出力は FrameWebforJS/CS の保存形式のJSONで、FEMPython の解析要求のJSONではありません。`FrameWebforCS.Headless.exe run --input <json> --output-dir <空の絶対パス>` が、保存形式から計算要求への変換・計算・Define/Combine/Pickup までを行います。FEMPython はこの中で使われる計算エンジンで、保存形式を直接は読みません。
- **読込みの確認**（2026-10-18、`scripts/check_frameweb_headless.py`、記録 `tests/fixtures/acceptance/frameweb_headless/record.json`）：`pre/input.json` と `current.json` の 0610・0620（両入力で同じバイト）を FrameWebforCS.Headless（FEMPython）で計算させ、節点・部材・Define・Combine・Pickup の数、荷重ケースごとの反力と書いた荷重の釣合い、0610 の組合せ1の上向きの鉛直反力（FEMPython 22585.1473、計算書 22585.160、作用ごとの丸めの差は最大0.005）を照合しました（座標を現行形式にした後に取り直し）。行のない荷重ケース5（低水位の浮力が0）とその Define 5 は FrameWeb が飛ばします。0620 は風荷重の終わる位置（y = 4.7 m）に FEMPython が節点を1つ加えます。読込みを確かめるための計算で、構造解析・照査の結果ではありません。生成する FrameWeb 入力が変わると `tests/acceptance` が失敗するので、確認をやり直します。
- 基礎の剛域は Example2 と同じく、明示した節点・部材に有限の剛性（E = 26,500,000 kN/m²、A = Iz = 1,000）を与えて表します。保存形式の `rigid` 配列は部材端の区間に別の断面を割り当てるだけで、剛体の拘束ではないためです。A・Iz を10倍・100倍にしても柱頭の変位が約0.004 mm 変わるだけで、反力・断面力はほとんど変わりません。
- `Xp` は熱膨張係数です。G・J・Iy の null は2次元への投影で1になります。荷重ケースの `rate` は計算要求に写されず、倍率として効きません（Example2 と同じく1を書きます）。
- FrameWebforCS の画面で保存し直すと、知らないトップレベルのキーは捨てられ、多くの数値が Single 精度に変わります（例：回転ばね 52,218,663 → 52,218,664）。付帯JSONのSHA256による保証は、画面で保存し直したファイルには及びません。別名で保存し、生成したファイルと付帯JSONの組を保管してください。

### Aggre-SE（プロジェクトXML）

0711・0721 の静的非線形解析の結果を Aggre-SE（structural-mcp の `Batch` サブモジュール、Docu-SE）で耐震照査するためのプロジェクトを、`post/線路方向.xml`・`post/線路直角方向.xml` に書きます（決定49、CONTEXT.md「耐震照査の入力」）。見本は Example2 の `10_線路(耐震)/P1_線路.xml`・`11_直角(耐震)/P1_直角.xml` です。同じ生成で Aggre-SE の runner がこの XML で照査し、その帳票が 0711・0721 の計算書になります（決定56）。

- 入力にするのは `耐震設計条件`（地域別・地盤区分）だけです。そのほかの条件は Example2 のプロジェクトと同じ WebPier の定めです。
  - スペクトルⅠ,Ⅱ両方、液状化指数 5<PL<20（液状化する杭基礎の 0711・0721 は入力の `耐震設計条件.液状化指数`、決定95）、M6.5以上の震源エリアなし、低減係数 α = 1.000、不整形性 η(x) は考慮しない
  - 照査項目 ①〜⑨ は Case の照査パターン（ρm, αf）で決まり、載荷の向きによりません（決定76）：①復旧性L2・②安全性L2 は全 Case、③損傷レベルは (1.0, 2.0) 以外、④破壊形態の検討は ρm 1.2、⑤せん断耐力はなし、⑥L1 は (1.0, 1.0)、⑦基礎の安定・⑧杭の段落し・⑨断面力ピックアップは αf 1.0
  - 非線形部材（柱下端の M-θ）の部材照査タイプは 2（柱）、せん断耐力式は ①RC標準。損傷レベルの制限値は梁・柱・杭の順に復旧性 2/2/2、安全性 2/3/2
  - 直接基礎の制限値は空欄（Aggre-SE が自動計算）、帳票はカスタム仕様
- NDU から決まる値：直接基礎の照査位置は FootInfo の節点（線路方向 7、線路直角方向 8）、せん断スパン La は柱の断面の L（7600・10350 mm。直角方向は制御節点まで。起点側・終点側の桁の高さが違えば桁の慣性力の大きい側の桁の高さ、決定81）、着目節点は 0（各 DB1 の着目点）です。
- 書式は Aggre-SE が保存するとおりです（Batch.exe 5.3.0.1 の `Input.GetXmlData` を Shift-JIS で書いたもの）。宣言は `encoding="utf-16"` ですが中身は Shift-JIS・CRLF で、ケースの配列は50件です。Aggre-SE の版が変われば書式を合わせます。

## Example2 との既知の差

現在の入力（`tests/fixtures/inputs/current.json`。`pre/input.json` も JRSNAP の解析設定のほかは同じ値）で Example2 と比べたとき、設計上残している差です。根拠はそれぞれのテストに書いています。

- **Example2 が丸めない中間値で印刷している箇所（0.01程度）**：WebPier は印刷された値から計算するので、Example2 の隠れた桁による差が残ります。例：08 p.8-4 の RB = 544.93（丸めない 272.4668 × 2）に対し 272.47 × 2.000 = 544.94。07 p.7-8・7-9 の 2851.85・7-11 の 2613.85 に対し 2851.84・2613.84。08 p.8-5 の 428.28 に対し 120.98 + 307.31 = 428.29。09 p.9-5 も同様です（`tests/calc/test_reaction_longitudinal.py`、`test_longitudinal_loads.py`、`test_transverse_loads.py`、`tests/export/test_frameweb_*loads.py`）。
- **橋脚く体の衝撃の低減（決定77）**：0610・0620 の衝撃荷重は、桁の衝撃係数 i0 に低減比 1 − Ds/(L + Du + Ds)（RC標準 解4.4.4、Example橋脚3 Ⅱ-2-6）を掛けた橋脚く体の係数 i を使います（L は両側の桁の列車荷重の和でρf を掛けず、Du は両側の桁の D1＋D2、Ds は柱下端までのく体の自重。比は3桁、Ds/(L＋Du＋Ds) が 0.9 以上なら i＝0）。Example2 は低減していないので、この橋脚の比 0.751（単線）・0.763（複線）の分だけ 8-5・9-6 の衝撃荷重（227.78 など）と、それを含む荷重図・組合せ・断面力・反力が違います。0600 の 6.3 (2) に低減の計算を印刷します。0900 と地震時には掛けません。

- **シェルター荷重の集約**：WebPier にシェルターの機能はなく、入力はシェルター分を支承の D1・D2・S2 に集約し、風の受風高さは h4（9.433 / 10.767）、直角方向の地震時の桁慣性力は等価重心高 hs = M/H（2.952 / 3.066）に含めています。
  - 風荷重の H は Example2 と一致します（列車ありの起点側 197.00 など）。列車なしの 393.99・217.76 は Example2 の 394.00・217.75 と0.01違います（h4 を3桁に逆算したため）。風荷重の M は、シェルターを鉛直の偶力として扱わず高さに含めるので Example2 と異なります（0620 の合計 M は列車あり 2124.50・列車なし 4248.93、Example2 9-7・9-8 は 1001.33・2002.64）。この差はユーザーが許容しています（`tests/calc/test_reaction_transverse.py`、`test_transverse_horizontal.py`）。
  - 直角方向の地震時の桁慣性力は、起点側 6720.00 × 2.952 = 19837.44（Example2 19838）、終点側 2370.00 × 3.066 = 7266.42（Example2 7267）です。終点側の H は Example2 の 2360 に対し +10 kN（原本の独立反力 640 kN と集約した D1＋S2 = 400＋250 = 650 kN の差）で、線路方向の一致を保つため入力は調整しません。0720 の EQ1 は Example2 11-8 の H = 9080.00・M = 27105.00 に対し H = 9090.00・M = 27103.86 になり、原本の桁本体とシェルター偶力の内訳行は再現しません（`tests/calc/test_seismic_transverse_actions.py`）。
- **はりハンチの重心**：幅と奥行きが直線的に変わる立体の厳密な式 z = ∫z·b·w dz / ∫b·w dz を使い、0.389 m です。Example2 は錐台の式で 0.390 m（相似な断面でだけ厳密）で、0.001 m 違います（決定22、`tests/calc/test_reaction_self_weight.py`）。
- **0610・0620 の D1 の内訳**：0600 のはり重量（直方体＋ハンチ全体、1503.27 kN）を天端に置き、柱の線荷重と重なる H2＋H3 = 2.700 m を控除します。Example2 8-3 ははり 1190.70 と張出しハンチ 104.19 を置いて H2 = 2.00 m だけを控除するので途中の合計は違いますが、天端の N = 8299.53 は一致します（`tests/calc/test_longitudinal_loads.py`）。
- **フーチングの張出しの地盤反力（12.1 の 3)）**：原資料（`0700_線路フーチング.xls`）の柱前面の反力度 q2 は `qd2 + (qd1 − qd2)·L1/X1`（qd2 側の縁から L1 の位置の値）ですが、WebPier は q1 側の柱前面の値 `qd1 − (qd1 − qd2)·L1/X1` を使います（決定60、ADR-0001。両者が一致するのは L1 = X1/2 のときだけ）。安全性・使用性の列の W・x・M・Md・Vd・La が見本より大きくなります（例：線路方向 安全性 Vd最大 Md 760.74 → 799.16、Vd 675.13 → 728.89）。地震時の列（Case 4）は q2 を使わないので一致します。照合は独立の手計算 `tests/fixtures/example2/footing_hand.json` で行います（`tests/calc/test_footing.py`）。
- **フーチングの使用性の列（12.1 の 1)）**：FEMPython の反力の Vd は 19506.36／18049.95 kN で、見本の 19505.93 とは隠れ桁の丸めで 0.4 kN 違います（受入 `scripts/accept_footing.py` の許容差は使用性の Vd だけ 0.5 kN）。鉛直力が同じ2つの極値（水平力の向き違い）は |mz| の大きい行を採るので、Md は見本（3327.13／3056.25）と一致します（決定60）。
