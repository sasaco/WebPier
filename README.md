# WebPier 鉄道橋脚の荷重計算

`pre/input.json`（schema 2）を読み、0500 直接基礎の地盤ばね、0600 上部工反力・橋脚自重、0610 線路方向荷重、0620 直角方向荷重、0710 地震時の線路方向荷重、0720 地震時の線路直角方向荷重を計算し、A4縦・白黒の計算書PDFと結果JSONを作成します。0610・0620 からは FEMPython / FrameWebforCS の入力、0710・0720 からは JRSNAP 5.2-L03 の入力（NDU）も作成し、その NDU を JRSNAP に読ませて描いたデータ確認図と荷重図のページを 0710・0720 の計算書に差し込みます。入力の出力項目（`outputs`）で骨組解析を選べば、0611・0621 でその FrameWeb 入力を FEMPython で骨組解析し、ピックアップ断面力・変位量・反力のファイルも作成します。0611 はさらに、そのピックアップで柱下端の断面照査を Capacita に行わせ、計算書（8.5〜8.9）と Capacita で開ける WDJ も作成します。0612・0622 は同じ骨組解析の支点反力で直接基礎の照査（鉛直支持・水平支持・回転）を行い、計算書（8.10・9.10）を作成します。静的非線形解析を選べば、0711・0721 で両方向の NDU を JRSNAP で静的非線形解析し、解析用データ（.NDT）と解析結果のファイルに加えて、その結果を Aggre-SE（structural-mcp の `Batch`、Docu-SE）で耐震照査するためのプロジェクトXMLも作成します。

計算はPython、計算書の組版は GridLayoutPdf、PDF描画はその ReportLab バックエンドです。実行時に Excel や元の xls・PDF は使いません。骨組解析は FEMPython、柱の断面照査は Capacita に任せ、WebPier はそのピックアップを設計応答値として基礎の安定計算に使います（[ADR-0006](docs/adr/0006-frame-analysis-by-fempython.md)）。**寸法・配筋の最適化は対象外**です。

用語は [CONTEXT.md](CONTEXT.md)、原則は [docs/adr/](docs/adr/)、決定事項は [.claude/docs/plans/refactoring-decisions.md](.claude/docs/plans/refactoring-decisions.md) を正とします。

## 実行

```powershell
uv run --project "." --locked python -m webpier                     # 入力の出力項目（outputs）の計算書を作る
uv run --project "." --locked python -m webpier --overwrite         # 既存の成果物を更新する
uv run --project "." --locked python "./run_design.py" --overwrite  # python -m webpier と同じ
```

### 出力項目（`outputs`、決定72、ADR-0011）

入力の `outputs` は12の項目で、どれも `true` か `false` です（全項目が必須、`null` は不可）。項目は、それが使う項目がすべて `true` のときだけ `true` にできます。違反と、全項目が `false` の入力は入力エラーです。コマンド・headless runner・structural-mcp・入力エディタのどれも、この項目だけに従います。

| キー | エディタの表示 | 段階 | 使う項目 |
|---|---|---|---|
| `ground_model` | 地盤のモデル化 | 0500 | — |
| `reactions` | 上部工反力及び橋脚自重 | 0600 | — |
| `longitudinal` | 線路方向の計算（地震時以外） | 0610 | `ground_model`・`reactions` |
| `longitudinal_frame_analysis` | 骨組解析も行う | 0611・0612 | `longitudinal` |
| `transverse` | 線路直角方向の計算（地震時以外） | 0620 | `ground_model`・`reactions` |
| `transverse_frame_analysis` | 骨組解析も行う | 0621・0622 | `transverse` |
| `longitudinal_seismic` | 線路方向の計算（地震時） | 0710 | `longitudinal` |
| `longitudinal_nonlinear_analysis` | 静的非線形解析も行う | 0711 | `longitudinal_seismic` |
| `transverse_seismic` | 線路直角方向の計算（地震時） | 0720 | `transverse` |

項目と段階の対応は `webpier/inputs/outputs.py`（項目と使う項目）と `webpier/pipeline/stages.py` の `OUTPUT_STAGES` が持ちます。

0611・0612・0621・0622 は骨組解析の段階です（決定46、ADR-0006）。0611・0621 は骨組解析に続けて柱の断面照査を行い（決定48、下記）、0612・0622 は同じ骨組解析の反力で基礎の照査を行います（決定54、下記）。同じ FrameWeb 入力を解析する段階（0611 と 0612、0621 と 0622）は解析を共有し、1回の生成で FEMPython を1回だけ呼び、ピックアップのファイルも1組だけ公開します（付帯JSONの `stage` は先の段階、`frame_analysis.stages` に使った段階）。出力項目 `longitudinal_frame_analysis`・`transverse_frame_analysis` で選びます（両方向を選ぶと、上の20ファイルに、0611・0612・0621・0622 の計算書・結果JSON、ピックアップのファイル6つ、`線路方向.wdj`・`線路直角方向.wdj`、付帯JSON8つが加わります）。0611 と 0612（0621 と 0622）は同じ項目で、一緒に作ります。同じ生成で一度だけ組み立てた FrameWeb 入力のバイトを、荷重図とは別の呼び出しで FEMPython の Headless runner（`run --generate-pdf false --generate-pik true --generate-pickup-displacement-csv true --generate-pickup-reaction-csv true`）に渡し、返った `pickup.pik`・`pickup-displacement.csv`・`pickup-reaction.csv` を、読み直しも再エンコードもせずにそのままのバイトで公開します（`result.json` は SHA256 とバイト数を確かめるだけで公開しません）。解析に失敗すると何も公開せずに止まります（終了コード 2）。解析しない生成は、前回のピックアップのファイルを消さずに残します（どの世代のものかは付帯JSONでわかります）。0610・0620 の計算書は骨組解析の有無で変わりません。

0610・0620 の荷重図は、同じ生成で書いた FrameWeb 入力を FEMPython の `FrameWebforCS.Headless.exe` に描かせて計算書に差し込みます（決定44、ADR-0005）。runner の絶対パスをリポジトリのルートの `.env`（git で追跡しません）に書いてください。プロセスの環境変数に同じ名前があればそちらが優先です。パスの区切りは `/` で書きます（VS Code のデバッグは `.env` を自分で読んで環境変数として渡し、その読み方では `\n`・`\b` などがエスケープになるので、`\` 区切りでは `\net10.0`・`\bin` が壊れて runner が見つかりません）。

```
STRUCTURAL_MCP_FEMPYTHON_RUNNER='C:/Users/<user>/Documents/structural-mcp/FEMPython/FrameWebforCS/Headless/bin/Release/net10.0-windows/FrameWebforCS.Headless.exe'
```

設定がない・runner がない・runner が荷重図を描けない（骨組解析できない）ときは、0610・0620（0611・0612・0621・0622）を含む生成は何も公開せずに止まります（終了コード 2）。荷重図や骨組解析を省いて続けることはしません。

0611（線路方向）・0621（直角方向）の柱の断面照査（決定48、ADR-0008）は Capacita（structural-mcp の `Capacita`、RcDan）が行います。2つの段階は方向（主鉄筋の面・側方鉄筋の面・帯鉄筋の行・断面の向き）と節の番号（0611 は 8.5〜8.9、0621 は 9.5〜9.9）だけが違います。WebPier は柱下端の1断面について WDJ を作り（断面・配筋・抽出ケースの対応・安全係数・ひび割れの条件・適用基準。断面力は持たない。柱下端の着目点の番号は PIK の着目点の並びから求め、断面力は読まない）、同じ生成の `線路方向.pik`（`線路直角方向.pik`）のバイトとともに `WebDanforCS.Headless.exe run-rc --output-format pdf --pickup <pik>` に渡します。Capacita は GUI の「断面力データ取込」と同じ変換でピックアップを取り込んで計算し、計算書（`report.pdf`）と、節ごとのページ範囲（`summary.reportSections`）と、取り込んだ完成の WDJ を返します。WebPier は 8.5〜8.9（9.5〜9.9）の見出しと解説（照査式・記号・曲げひび割れの検討のフローチャート）だけを描き、それぞれの後に Capacita の計算書のその節のページを差し込みます（8.5 断面力の総括、8.6 安全性（破壊）の曲げ・せん断、8.7 耐久性の曲げひび割れ・せん断ひび割れ、8.8 使用性（外観）、8.9 復旧性の曲げ・せん断）。外観の照査を「行わない」入力では 8.8 を置かず、8.9 の番号はそのままです。Capacita が断面力0で照査を飛ばした節（RC標準の省略の規則。Capacita は節を返さず、info のメッセージ WD-1901〜1908 で理由を返す）は、見出しと解説の後に省略の理由の1文を印刷し、ページは差し込みません（Example2 の 0621 では、永久作用が左右対称なので 9.7(2) せん断ひび割れと 9.8 使用性）。直角方向の側方鉄筋が隅の鉄筋を含んで間隔が両端だけ違うとき（Example2 の線路の D32）は、見本どおり位置を書かずに本数だけを書き、Capacita が上下の主鉄筋の間に等分に配置します。解説には WDJ に書いた γi・γb・kr・k4・ε'csd と入力の環境条件を印刷し、Capacita の中にだけある制限値の表は印刷しません（使った値は差し込むページにあります）。完成の WDJ は `post/線路方向.wdj`（`post/線路直角方向.wdj`）として付帯JSONとともに公開し、Capacita の GUI で開けます。Capacita は照査値も判定も返さないので、結果JSONには照査を実行したことだけを `section_check`（`engine`・`engine_version`・`engineering_status: not_evaluated`・公開した WDJ のファイル名と SHA256）に、飛ばした節を `skipped_sections` に記録します。判定は計算書のページで確かめてください（NG でも生成は止まりません）。runner の絶対パスは `.env` に書きます（structural-mcp と同じ旧名。プロセスの環境変数が優先）。

```
STRUCTURAL_MCP_WEBDAN_RUNNER='C:/Users/<user>/Documents/structural-mcp/Capacita/WebDanforCS/Headless/bin/Release/net8.0/WebDanforCS.Headless.exe'
```

0612（線路方向）・0622（直角方向）の基礎の照査（決定54、CONTEXT.md）は WebPier が行い、計算書（0612 は「8.10 基礎の照査」、0622 は「9.10」）をすべて WebPier が描きます。設計応答値は、骨組解析の `*_ピックアップ反力.csv` のうち、フーチング底面の中心のばね支点（骨組の役割から求める）の反力です（Vd＝−fy、Hd＝|fx|、Md＝|mz|。読むときに印字桁の2桁へ丸める。WebPier で荷重から組み立て直さない）。列は見本 8-30 と同じ4つで、抽出ケースから取ります：長期支持（7）と短期支持（8）は鉛直反力が最大の組合せ、安全性は 6 安定の鉛直反力が最大の組合せ（鉛直力最大）とモーメントの絶対値が最大の組合せ（曲げ最大）。鉛直支持は γi・γa・pd1／qd（長期・短期）と γi・γa・Vd／Rvd（安全性）、回転は γi・γa・ex／制限値（長期 B/6・短期 B/4）と γi・γa・Md／Mmd（安全性、Mmd＝Vd・B/2・(1 − Vd／(qd・B・L))）、水平支持は γi・Hd／Rhd（Rhd＝Rhb＝frs・Vd・tanφ、全列 γi＝1.0）で照査します。qd は見本の「砂質土の場合」の式（qvd＝frγ・Iγ・βb・Be・γe1・Nγ＋frq・Iq・γe2・Df・(Nq−1)、qd＝qvd＋γe2・Df）で、支持層は砂質土・砂礫だけに対応します（粘性土・互層は入力エラー）。長期の qd の上限値は支持層の土質区分から決めます（砂質土は洪積砂地盤・沖積砂礫地盤で 300＋γe2・Df、砂礫は洪積砂礫地盤で 500＋γe2・Df）。Df は 0500 の表層厚、γe2 は長期支持が平水位、短期支持と安全性が高水位で求めます（CONTEXT.md「有効根入れ深さと平均有効単位重量」）。地盤抵抗係数・γi・γa・回転の制限値はプログラムの定数です。照査値と判定（ＯＫ／ＮＧ）を表に印刷し、結果JSONの `result` に列ごとの値と `engineering_status`（すべて満足で `ok`、1つでも NG なら `not_ok`）を記録します。NG でも生成は止まりません。反力の CSV を読めない・支点のピックアップが欠ける・合力の作用位置がフーチングの外にある・鉛直力が上向きのときは、何も公開せずに止まります（終了コード 2）。

### structural-mcp から使う（headless runner、決定61）

structural-mcp（MCP の `webpier_get_input_schema`・`webpier_get_contract`・`webpier_validate`・`webpier_generate`）は、repo のルートの `run_headless.py` を venv の python で起動します。直接呼ぶ場合も同じです。

```powershell
.venv\Scripts\python.exe -X utf8 .\run_headless.py run --input pre\input.json --output-dir <空のフォルダー>
.venv\Scripts\python.exe -X utf8 .\run_headless.py validate --input pre\input.json
.venv\Scripts\python.exe -X utf8 .\run_headless.py contract
.venv\Scripts\python.exe -X utf8 .\run_headless.py schema
```

- stdout は JSON 1つ（protocol v1 の envelope、`engine: "webpier"`）。`run` は `--output-dir` の下に `output/`・`post/`・`export/` を CLI と同じ配置・同じバイトで書き、`artifacts` に全ファイルの相対パス・SHA-256・サイズを返します（JRSNAP の結果フォルダーは中のファイルを1つずつ）。
- 作る段階は入力の出力項目だけで決まり（決定72）、`summary.outputs` に選んだ項目を返します。`--stage` などの選択の引数はありません（付ければ `INVALID_ARGUMENT`）。
- runner は**環境変数だけ**から読みます（`.env` は読みません）。選んだ出力項目が要る runner がなければ何も書かずに `RUNNER_UNAVAILABLE` で終わります。
- 終了コードは CLI と同じ（0・2・3）。失敗の種類は `errors[0].code`（`INVALID_ARGUMENT`・`INPUT_ERROR`（入力のパス付き）・`ADDIN_ERROR`（下の「荷重モデルのアドイン」）・`RUNNER_UNAVAILABLE`・`ENGINE_FAILED`・`GENERATION_FAILED`・`IO_ERROR`・`RECOVERY_REQUIRED`）。
- `engineeringStatus` は段階ごと（0612・0622 は ok／not_ok、ほかは not_evaluated）と全体（not_ok が1つでもあれば not_ok、判定した段階がすべて ok なら ok）。実行の成否（`ok`）とは別です。
- `validate` は runner を呼ばずに決まる範囲（解析・計算・外部出力・Aggre-SE のプロジェクトの入力）を確かめます。`contract` は段階（依存と出力項目）と、出力項目ごとの段階・使う項目・選ぶと要る runner（使う項目の分も含む）・公開するファイル（`outputs`）、`schema` は入力の JSON Schema（項目表から。必須と項目間の規則は `validate` が正）。

### 荷重モデルのアドイン（`--addin`、決定70、ADR-0010）

死荷重以外の支承作用と作用の組合せは、荷重モデルとして差し替えられます（CONTEXT.md の 荷重モデル・支承作用）。案件の荷重モデルは案件の repo に置くアドインで、`--addin <フォルダー>` で読み込みます。付けなければ、いままでどおり列車荷重で計算します（成果物は1バイトも変わりません）。

```powershell
uv run --project "." --locked python -m webpier --addin <アドインのフォルダー> --overwrite
.venv\Scripts\python.exe -X utf8 .\run_headless.py run --input pre\input.json --output-dir <空のフォルダー> --addin <アドインのフォルダー>
.venv\Scripts\python.exe -X utf8 .\run_headless.py contract --addin <アドインのフォルダー>   # validate・schema も
```

- アドインのフォルダーには `webpier-addin.toml`（`name`・`version`・`contract`（約束の版、いまは 1）・`entry = "モジュール:関数"`）と、そのモジュール（`<モジュール>.py` かパッケージ）を置きます。関数は引数なしで、`calculate(context) -> LoadModelResult` を持つものを返します。アドインが import してよいのは `webpier.loadmodel` だけです。見本は `tests/fixtures/addin/minimal/`。
- 約束（`webpier/loadmodel/`）：基本ケースごと・支承ごと（起点側・終点側 × 支承の枠 1〜10）の支承作用（鉛直力、線路方向・直角方向の水平力とその作用高さ。力は小数2桁、高さは3桁の Decimal）、基本ケースのばね（長期・短期）と地震時の固定・増分・限定増分と向き、骨組（0610・0620）の組合せと8つの抽出ケースへの割り当て、地震時（0710・0720）の組合せ、片持ち梁（0900）の組合せと Capacita の力の表の8行への割り当て（係数に最大応答震度 `MaxResponse` も可）、計算書に差し込む根拠の節（段落と文字の表）、来歴の辞書。組合せからは、アプリの基本ケース `D1`・`D2`・`WP_HIGH`・`WP_NORMAL`・`WP_LOW`（骨組）、`PIER_WIND_<n>`（0620 の躯体の風、`pier_wind_pressures` の n 番目の風圧）、`EQ2`（地震時の橋脚自重の慣性力）を id で参照します。
- アプリは結果を受け取るときに検査し（`loadmodel.validate`）、違反は `アドイン:<場所>` の入力エラーにします（id の一意、参照先、空き支承枠、印字桁、符号 −1 は鉛直力0のケースだけ、地震時のケースは NDU の15まで、ほか）。
- 0600 は死荷重・自重だけ、0610・0620・0710・0720・0900 は荷重モデルの結果から作り、それ以外の段階は同じものを使います（`pipeline.stages.stages_for`）。支承作用は M = N × アーム ＋ H × y で支承位置に集めた橋脚天端の等価作用にします。組合せのない抽出ケースは荷重0のケース（`ZERO`、FrameWeb には ty = 0 の1行）で断面力0として通し、計算書に「該当する組合せなし（断面力0）」と印字します。Vd＝0 で割る照査（基礎の照査、フーチング）は抽出ケースの名前を入れた入力エラーです。0720 の制御節点の重みは、増分の地震時ケースの直角方向の支承作用を起点側・終点側ごとに合計したものです。
- アドインをつないだとき、入力の荷重モデルの項目（`列車`、各側の `衝撃係数_単線終局`・`曲線半径`・`列車速度`・`遠心作用方向`、支点・支承の雪荷重と `列車分担`）は読みません（検査も印字もしない。あってもなくてもよい）。入力エディタはアドインに対応しません（エディタの「計算・印刷」は列車荷重で計算します）。
- 来歴：アドインが宣言した名前・版・約束の版と、アドインが返した来歴の辞書を、解釈せずに全結果 JSON・全付帯 JSON と runner の `summary.addin` に `addin` として写します。アドインのファイルのハッシュは取らず、アドインの入力も読みません（アドインの責任）。
- 失敗：宣言がない・約束の版が違う・import や `calculate` が例外を出すと `ADDIN_ERROR`（終了コード 2）。アドインが自分の入力の誤りを `LoadModelInputError` で知らせると `INPUT_ERROR` です。
- `schema --addin` は荷重モデルの項目に `x-webpier-load-model: true` を付け、どの値でもよいとします。

## 入力（schema 2）

`pre/input.json` は `schema_version: 2` です。parser（`webpier/inputs/parse.py`）は入力を一度だけ検査し、各段階はその結果を共有します。

## 計算の原則

- **元Excelの誤りは再現しません**（ADR-0001）。WebPier は元Excel（0500〜0720のxlsと転記VBA）を基にしていますが、正規の計算は工学的に正しい式を使います。元式を意図的に残す箇所は、下の互換一覧に理由とともに書いたものだけです。
- **物理量で計算します**（ADR-0002）。元Excelのセル番地、セルの再生、元Excelから採取した照合値は使いません。期待値は Example2 の原資料から独立に転記した値と、実装を使わない手計算だけです。
- **印字桁で計算します**（ADR-0003）。計算書に印刷する値は内部でも印字桁に丸め、後続の計算はその丸めた値を使います。合計・積は印刷された部分の値から求め（0.125 の3行は各 0.13、合計 0.39）、段階間の引継ぎも前段の計算書に印刷された値で行います。印刷しない中間値は作りません。例外は移動荷重の載荷位置の探索で、探索の内部は丸めず、採用した結果を印字桁に丸めて印刷します。丸めは四捨五入（0.5は絶対値の大きい側）だけで、VBA の Single 精度、Excel の ROUND、偶数丸めは使いません。印字桁は計算器（`webpier/calc`）が値ごとに持ち、帳票は丸め直しません。
- **欠けた値を補いません**（決定5）。計算中に成立しない条件（0除算、表の範囲外など）も入力エラーにします。例：コンクリートのヤング係数 Ec は f'ck 18〜80 N/mm² の表の線形補間だけで、範囲外は入力エラー（決定25）。複線の衝撃低減 1 − L/200 は L ≥ 200 m を入力エラー（決定13）。

### 互換一覧

元Excelの式を意図的にそのまま再現する箇所（**元式の互換動作**、CONTEXT.md）の一覧です。元Excelを意図して再現する箇所は、必ずここに理由とともに書きます（ADR-0001）。ここにない元Excelとの差は、すべて誤りとして直したものです。

いまは**ありません**。以前の4点のうち、可動支承の水平力の下限 μ·T/n は正しい設計式として本文の規則にし（決定11）、残る3点（柱下端の集計の桁受けを重量で集計、直角方向のモーメントに桁受けを含める、上載土の xL に線路方向の重心を使う）は元Excelの誤りとして直しました（決定20）。

## 構成

### 層別パッケージ（ADR-0004）

```
webpier/
  core/       Printed（印字桁つきの値）、厳密なJSON読込み、エラー、ハッシュ
  inputs/     schema 2 の解析と検証。項目表 fields.py、選択肢 choices.py
  loadmodel/  荷重モデルの約束（アドインが import してよい唯一のパッケージ）と結果の検査（決定70）
  calc/       段階の計算（foundation, reaction, longitudinal, transverse, seismic_*）と共通の骨組・移動荷重。
              generic/ は荷重モデルの 0610・0620・0710・0720・0900、bearing_actions は支承作用から橋脚天端の等価作用
  reporting/  GridLayoutPdf による計算書（stages/ に段階ごとの組版）
  export/     frameweb/（FEMPython・FrameWebforCS）、jrsnap/（JRSNAP 5.2-L03 NDU）、aggrese/（Aggre-SE のプロジェクトXML）
  pipeline/   段階の登録表、生成、公開、CLI（python -m webpier）
  gui/        入力エディタ（python -m webpier.gui）
```

依存は `core ← inputs ← loadmodel ← calc ← reporting / export ← pipeline ← gui` の向きだけです（loadmodel は core だけに依存し、モジュールを名前で import する importlib は pipeline だけが使います）。`tests/test_layer_boundaries.py` が強制し、calc・inputs・core は描画や Tk のライブラリも import しません。計算は帳票に依存しません。

### 段階の登録表

段階の依存・計算・帳票・成果物・外部出力は `webpier/pipeline/stages.py` の `StageSpec` の表1か所に定義します。生成・成果物の一覧はすべてこの表から作るので、段階や外部出力の追加は表の1項目です。`calculate` と `render` には宣言した依存段階の結果だけを渡すので、宣言していない依存は動かずに失敗します。計算書のない段階（`render` なし）、依存段階の FrameWeb 入力の骨組解析（`frame_analysis`）、依存段階の NDU の静的非線形解析（`nonlinear_analysis`。返ったファイルを1つのフォルダーで公開する）も表の項目で表します。各段階は1つの出力項目に属し（`Registry.outputs`、既定は `OUTPUT_STAGES`）、登録表は、段階が自分の項目とその項目が使う項目の段階だけを読むことを確かめます（決定72）。そのため、選んだ項目の段階が生成で計算する段階のすべてです。

### 生成と一括公開

1. 入力を一度だけバイト列で読み、厳密に解析します（重複キー・NaN・Infinity は入力エラー）。そのSHA256を全ての結果JSONと付帯JSONに記録します。
2. 入力の出力項目で段階を選び（決定72）、出力先をすべて検査してから計算を始めます。同名のディレクトリやシンボリックリンク、入力と同じパスの出力は拒否します。
3. 選択した段階をすべて計算してから描画します。保存済みの結果JSONは読みません。荷重図のある段階（0610・0620）は、ステージングした FrameWeb 入力を FEMPython の runner に描かせ、そのページを計算書に差し込みます。データ確認図と荷重図のある段階（0710・0720）は、同じ生成で組み立てた NDU を JRSNAP の runner に描かせ（データ確認図と荷重図を1回の呼び出しで）、同じく差し込みます。骨組解析の段階（0611・0612・0621・0622）は、同じ生成で組み立てた FrameWeb 入力を runner に解析させ（荷重図とは別の呼び出し。同じ入力は1回だけ）、計算書を描く前に結果を確かめます。0612・0622 はその反力で基礎の照査を仕上げてから描きます。0611 は続けて、その PIK と WebPier が組み立てた WDJ を Capacita の runner に渡し、返った計算書の節のページを計算書に差し込みます。静的非線形解析の段階（0711・0721）も同じく、同じ生成で組み立てた NDU を JRSNAP の runner に解析させます。runner は計算を始める前に探します。
4. 計算書・結果JSON・外部ソフト向け入力・付帯JSON・JRSNAP のフォルダーを各出力先の横でステージングし、`webpier/pipeline/publication.py` がまとめて公開します。旧ファイル（旧フォルダー）を同じファイルシステム内に退避して置き換え、公開した実バイト・入力・実装の同一性を最後に確かめます。フォルダーの実バイトは、中の全ファイルの SHA256 で確かめます。失敗すれば旧ファイルをすべて戻し、その実行で新しく作ったファイルは消します。複数ファイルがOS上で一瞬に切り替わる仕組みではありません。
5. 強制終了や復元の失敗では、出力先ごとの `.webpier-*` に `publication-pending`・`publication-journal.json` と退避ファイルを残し、次の実行はそれを見つけて止まります。journal の各 `destination`・`backup`・`had_original` を照合して旧成果物を戻すか、一式を別の場所へ保全してから再実行してください。

結果JSON（`output/<段階>.json`）は `schema_version`・`stage`・`input`（ファイル名とSHA256）・`implementation_sha256`・`result` を持ちます。付帯JSON（`post/*.provenance.json`）は、その外部入力のファイル名とSHA256、入力のSHA256、実装のSHA256、選択した段階、同じ世代の全成果物（役割・出力先・ファイル名・SHA256）を記録します。FrameWeb 入力の付帯JSONには、それを描いて計算書に差し込んだ runner の版（`load_diagram.engine_version`）も記録します。NDU の付帯JSONには、データ確認図と荷重図を描いた runner の版と報告（`jrsnap_figures`：差し込んだ計算書 `report`、`engine`・`engine_version`、データ確認図の組合せと図 `data_check`、荷重図のケースと組合せ `load_diagram`、`runner_summary`）を記録します。骨組解析のファイル（`*.pik`・`*_ピックアップ変位量.csv`・`*_ピックアップ反力.csv`）の付帯JSONには、`frame_analysis` に runner の版（`engine_version`）と、解析した FrameWeb 入力の段階・種類・ファイル名・SHA256（`frameweb`）と、そのファイルを使った選択段階（`stages`）を記録します。`線路方向.wdj` の付帯JSONには、`section_check` に Capacita の runner の版、`engineering_status: not_evaluated`、取り込んだ PIK（段階・種類・ファイル名・SHA256）と WebPier が渡した WDJ の SHA256（`wdj_given`）を記録します。`frame_analysis.frameweb.sha256` が、解析結果とその FrameWeb 入力を結び付けます。実装のSHA256は、`webpier` のソースと、インストール済みの GridLayoutPdf・ReportLab・Pillow・pypdf・書体ファイルのバイトから求めます（`webpier/pipeline/runtime.py`）。生成中にこれらが変わると公開しません。FEMPython・JRSNAP・Capacita の runner はここに含めません（その出力はそれぞれの責務、決定44・46・47・48）。JRSNAP のフォルダーの付帯JSONは上の「0711・0721」の段落のとおりで、`nonlinear_analysis.ndu.sha256` が解析結果とその NDU を結び付けます。

PDFは作成日時を含まないので、同じ入力・書体・ライブラリからは毎回同じバイトになります。例外は 0610・0620 に差し込む FEMPython の荷重図のページと、0710・0720 に差し込む JRSNAP のデータ確認図と荷重図のページ（ヘッダーに印刷日が入るので、日ごとにバイトが変わります）で、その中身はそれぞれの責務として毎回同じバイトになることを求めません。計算書にはページ番号を印刷しません（体裁の見本どおり）。

## 計算書

計算書はA4縦・白黒で、GridLayoutPdf 0.2.0 の共通グリッド（16.08×15.48pt のマス、30列×47行）に組みます。字下げ・等号・表の列幅と行高はマスの数で決まり、構成・文言・式の書き方は `.claude/docs/Example橋脚/output` に合わせます。数値・式・ケースは現在の入力から計算します。計算内容の見本は `.claude/docs/Example橋脚2` です。式・表・図のまとまりを保って改ページするので、ページ数は内容に応じて変わります。文字の縮小や伸縮で固定ページ数に収めることはしません。体裁の契約は [.claude/docs/reporting-style.md](.claude/docs/reporting-style.md) にあります。

WebPier が組む頁は、同じものを方眼Excel `export/<段階>.xlsx`（1冊1シート。セルが方眼のマスで、文字・式の項・表の罫線がセルに入る）にも書きます。他のプログラムの頁（FEMPython の荷重図、Capacita・JRSNAP の頁）は入りません。0711・0721 は Aggre-SE の帳票そのものなので、方眼Excel はありません。出し先は `--export-dir`（既定は出力先と並ぶ `export`）。方眼Excel は GridLayoutPdf の strict で書き、セルに置けない部分が1つでもあれば、何も公開せずに止まります。

各帳票の内容は Example2 の対応する計算書に合わせています（0500: 04 地盤のモデル化、0600: 05・07、0610: 08、0620: 09、0710: 10、0720: 11）。

- 0500 は地盤ばね（kv・Kv・ks・Ks・Kr、長期・短期、2方向）と支持力係数（解説表13.2.2.3-2、表の中間は線形補間、42度以上は Nγ=150・Nq=85）を計算し、土質区分の係数・指数を印刷します。平坦な土被りでは、JRSNAP に渡す有効根入れ深さ Df と平均有効単位重量 γ2 = ((Df − hw2) × γwet + hw2 × γsub) / Df も印刷します（CONTEXT.md）。Df の範囲に複数の層があるときは、層ごとの水位より上・下の厚さで加重平均した γ2 = Σ(hi × γi) / Df です（支持層より上の層は層厚を入力し、支持層は Df の残り。決定64）。
- 0600 は死荷重・雪荷重（2・10・30年確率）、橋脚自重・上載土・浮力、移動荷重の反力、方向別の荷重を計算します。桁受けは体積 V = 0 のとき、その項と集計表の行を省き、後続の項の番号を詰めます。本橋脚の支承の表は空き支承枠を除き、支承は入力の枠の番号（G1〜G10）で示します（決定41）。
- 0610 は20基本ケース・20 Define・16組合せ・8抽出、0620 は17基本ケース・15 Define・16組合せ・8抽出です。この橋脚の支承に雪荷重がなければ、雪荷重の基本ケース（0610・0620 の 6〜8）と Define を作らず、後の番号を詰めます（0610 は17基本ケース、0620 は14基本ケース・12 Define。組合せと抽出は変えません。決定69）。組合せは「用途別解決」として、各成分を印刷された係数×印刷された基本作用で求め、N・H・M・q ごとに一度だけ印字桁に丸めます。0620 の単線の成分は組合せの中で上り線・下り線のどちらか一方にそろえ、車両横荷重と風の正負は独立に選びます。
- 0710 は8基本ケース・1組合せ（地震は起点側 ← の片方向）、0720 は9基本ケース・上り線・下り線それぞれの2組合せ（地震は → の片方向）です（決定21・30）。雪荷重がなければ CASE-4 雪荷重を作らず、後の CASE を詰めます（0710 は7、0720 は8基本ケース。決定69）。どちらも柱下端の0.010 mの微小部材（CONTEXT.md）を骨組図に示します。
- 荷重図（0610 の 8.3、0620 の 9.3、決定44）：見出しだけを WebPier が組み、その後に FEMPython が FrameWeb 入力から描いたページ（A4縦、1ページに2ケース、軸線図なし）をそのまま差し込みます。描くのは FrameWeb 入力の全荷重ケースで、基本ケースのほか使用性の衝撃（`I1s` など）も含みます。次の節（組合せ、8.4・9.4）は新しいページから始めます。Example2 のように複数ケースを1図にまとめて値を右に並べる体裁にはしません。
- Example2 にあっても WebPier が描かないもの（決定41）：0710・0720 のばね（骨組図のばね記号、Kv・Ks・Kr、ばねの表と数値）、0720 の柱下端の拡大図。WebPier の図がばねを示さないことは、固定基礎や解析可能な支持条件を意味しません。JRSNAP に渡した節点ばねは、差し込むデータ確認図の節点ばね分布図（Example2 10-7・11-7 にあたる、決定50）に JRSNAP が描きます。
- データ確認図（0710・0720、決定50）：Example2 10-3〜10-7・11-3〜11-7 にあたる JRSNAP のページです。Example2 の 1・2 ページ（節点番号図・要素番号図）は、WebPier の骨組図と重なるので入れません。
- 荷重図（0710 の 10.3、0720 の 11.3、決定51）：見出しだけを WebPier が組み、その後に JRSNAP（`S_LoadPicture.exe`）が描いたページをそのまま挟みます。Example2 10.3・11.3 は Excel の図で1ページに2〜3ケースを載せていますが、その体裁は再現しません。作画条件は A4縦・縮尺自動・1ケース1ページ・すべて黒・ページ番号なしで、ほかは JRSNAP の既定値です。基本ケースを CASE の順に、そのケースを使う最初の組合せの .NDT から描きます（0710 は CASE-1〜8 を組合せ1から、0720 は CASE-1〜9 のうち CASE-6 だけを組合せ2から）。次の節（作用の組合せ、10.4・11.4）は新しいページから始めます。

## 外部ソフト向けの入力

### FrameWeb（FEMPython / FrameWebforCS）

0610 から `post/線路方向.json`、0620 から `post/線路直角方向.json` を作ります。形式は Example2 の FrameWeb 保存ファイル（`.claude/docs/Example橋脚2/08_線路/frameWebForJS.json` など）に合わせています。規則の詳細は `webpier/export/frameweb/` の各モジュールに書いています。

- **座標は現行の FrameWeb 形式（y は下向き）です**（決定44）。Example2 は旧形式（y 上向き）で保存されていますが、FEMPython（FrameWebforCS/Headless・FramePrintPDF）はどの保存ファイルも現行形式として扱うので、旧形式のままでは荷重図が上下逆に描かれます。節点の y、節点荷重の ty・rz、部材荷重の gy の符号を反転して書きます（tx・gx はそのまま）。橋脚を上下に鏡に映しただけなので解析結果は同等です（組合せ1の上向きの鉛直反力は反転の前後とも 22585.1473）。`ver` は書かないので、FrameWebforJS（ブラウザ版）で開くと旧形式とみなされてもう一度反転し、上下逆になります。
- 荷重ケースごとに地盤ばねの組（1 = 長期、2 = 短期）を選びます。ばねは荷重の性質で決め、ロングレールは長期、制動・始動などの活荷重は短期です（決定36）。
- FrameWeb のばねの値1は固定支点、0は自由を意味するので、ばねは正で1以外の値が必要です。荷重のない部材行は書きません。部材荷重の強度は FrameWeb が 0.01 に投影します。行のない荷重ケースは FrameWeb が飛ばすので、そのようなケースだけの Combine は落ち、その Pickup は失敗します。Combine の表は Define 50列までです。こうなる入力は公開前にエラーにします。
- **FrameWeb は係数×荷重を丸めずに組み合わせます**。計算書は作用ごとに係数×作用を印字桁に丸めるので、FrameWeb の組合せは計算書の印刷値と作用ごとに最大0.005程度ずれます。外部の解析ソフトとしてこの差を許容します（決定38）。
- **0620 の FrameWeb は Example2 の Define の構成のままです**（列車・衝撃・遠心を線ごとに独立に選ぶ）。そのため上り線の列車と下り線の衝撃の組も選びうるので、FrameWeb の包絡は、同じ線どうしだけを組み合わせる計算書より安全側に出ます（決定39）。FrameWeb の形式には Define 同士の選択を連動させる項目がなく（Define・Combine・Pickup の知らないキーは読込みで拒否されます）、各 Define は独立に包絡されるので、同じ線どうしに限定できません。
- 出力は FrameWebforJS/CS の保存形式のJSONで、FEMPython の解析要求のJSONではありません。`FrameWebforCS.Headless.exe run --input <json> --output-dir <空の絶対パス>` が、保存形式から計算要求への変換・計算・Define/Combine/Pickup までを行います。FEMPython はこの中で使われる計算エンジンで、保存形式を直接は読みません。
- **読込みの確認**（2026-10-18、`scripts/check_frameweb_headless.py`、記録 `tests/fixtures/acceptance/frameweb_headless/record.json`）：`pre/input.json` と `current.json` の 0610・0620（両入力で同じバイト）を FrameWebforCS.Headless（FEMPython）で計算させ、節点・部材・Define・Combine・Pickup の数、荷重ケースごとの反力と書いた荷重の釣合い、0610 の組合せ1の上向きの鉛直反力（FEMPython 22585.1473、計算書 22585.160、作用ごとの丸めの差は最大0.005）を照合しました（座標を現行形式にした後に取り直し）。行のない荷重ケース5（低水位の浮力が0）とその Define 5 は FrameWeb が飛ばします。0620 は風荷重の終わる位置（y = 4.7 m）に FEMPython が節点を1つ加えます。読込みを確かめるための計算で、構造解析・照査の結果ではありません。生成する FrameWeb 入力が変わると `tests/acceptance` が失敗するので、確認をやり直します。
- 基礎の剛域は Example2 と同じく、明示した節点・部材に有限の剛性（E = 26,500,000 kN/m²、A = Iz = 1,000）を与えて表します。保存形式の `rigid` 配列は部材端の区間に別の断面を割り当てるだけで、剛体の拘束ではないためです。A・Iz を10倍・100倍にしても柱頭の変位が約0.004 mm 変わるだけで、反力・断面力はほとんど変わりません。
- `Xp` は熱膨張係数です。G・J・Iy の null は2次元への投影で1になります。荷重ケースの `rate` は計算要求に写されず、倍率として効きません（Example2 と同じく1を書きます）。
- FrameWebforCS の画面で保存し直すと、知らないトップレベルのキーは捨てられ、多くの数値が Single 精度に変わります（例：回転ばね 52,218,663 → 52,218,664）。付帯JSONのSHA256による保証は、画面で保存し直したファイルには及びません。別名で保存し、生成したファイルと付帯JSONの組を保管してください。

### JRSNAP（5.2-L03 NDU）

0710 から `post/線路方向.ndu`、0720 から `post/線路直角方向.ndu` を CP932・CRLF で作ります。柱下端の0.010 mの微小部材を M-θ 部材とし、その断面は柱の配筋（方向別の鉄筋配置表）と入力条件から JRSNAP が自動算定します。他の部材は剛域、基礎は 0500 の短期 Ks・Kv と FootInfo（Df・γ2 など）による非線形回転ばねです（CONTEXT.md「JRSNAP入力モデル」）。

- 解析設定（分割数・制限ステップ・目標変位）は入力です（決定40）。ソルバーの数値制御（荷重分割1000、試行回数999、収束判定0.001）は設計条件ではないので、出典つきのプログラムの定数です。
- 上載土はフーチング重心に載荷します。非対称な基礎の斜めの剛部材は、鉛直と水平の2本の剛部材に分けて出力します（決定40）。
- JRSNAP は鉄筋配置表の先頭と末尾の段を引張鉄筋とみなし、面を区別しません。着目方向の主鉄筋がちょうどその段にならない配置（主鉄筋より外側や段のあいだの側面鉄筋）は表せないので、入力エラーにします。配置表の変更（決定68）は当てた後の鉄筋で表を作ります。
- 部材係数 γb（Vcd・Vsd・Vdd）の説明書の標準値は 1.3・1.1・1.2 で、Example2 の 2.0・1.3・1.8 とは異なります。どちらも補わず、必須の入力です。
- 対象の版は JRSNAP_Input.exe 5.2-L03（FileVersion・ProductVersion 5.2.3.0、AssemblyVersion 5.2.3.1）で、保存のヘッダは `Virsion=5.2.3.S.4`（キーの綴りは JRSNAP のまま）です。Example2 の NDU は 5.1.10 の保存で、5.2-L03 は DataInfo（23→26欄）、SectInfo（12→14欄）、SectSafe（11→12欄、GBVO = 1.3）、FootInfo（12→14欄、KR3 = 20 と未設定値 −3.402823E+38）の末尾に欄を加えます。
- JRSNAP は NDU を先頭から順に読むので、レコードの順序は変えられません。`Tisou=` は TishouNum = 0 でも空のまま必要です（消すと読込みで例外になります）。`TanbuShiji=0,0` は断面のせん断耐力の算定に使う支持条件で、骨組のばねとは関係ありません。
- 固定の設定値の根拠は Example2 の NDU と JRSNAP 5.2-L03 の操作説明書（`.claude/agents/jrsnap-operator/JRSNAP_Ver5.2-L03/JRSNAP_操作説明書.pdf`）です：座標 p.38、M-θ の集約 p.32–33、剛域の初期値 1000 m²・1000 m⁴・25 kN/mm² p.144–145、直接基礎の回転ばね KR2 = 2・最終勾配 1/20 p.155・515、La/d＜2 の破壊形態「せん断」と M-θ の名前20バイト p.142–143（La/d＜2 は `NonLinInfo1` の第4欄を 2 にし、1.25 未満は入力エラー。付録4、決定66）、件数の上限 p.29、SectConc の第5欄（粗骨材最大寸法）p.90・529。
- 通常の生成は NDU を書き、データ確認図と荷重図のために（決定50・51）runner が JRSNAP の読込みで .NDT を作りますが、解析はしません（0711・0721 を除く）。付帯JSONの `app_read_verified`（受入での読込み・保存・読戻しの確認）と `analysis_run` は常に false です。
- **実アプリでの受入**（決定4、2026-10-18、`scripts/accept_jrsnap_ndu.py`、記録 `tests/fixtures/acceptance/jrsnap_v52/`）：`current.json`（Example2 の解析設定）の両方向の NDU の複製を、JRSNAP_Input.exe 5.2-L03 の読込み・保存の処理（スキル `jrsnap-input-open-save`、画面は操作しない）で読込み・保存・再保存しました。保存した NDU は全レコードが同じ順序・同じ値で、違いは JRSNAP の数値の書式（`GanmaA=1.2,1,1,1` → `1.20,1.00,1.00,1.00`）だけです。2回目の保存は1回目とバイト単位で同じです。読込み直後に JRSNAP が保持する件数と組合せ（`scripts/jrsnap_state_probe.cs`）も書いたものと一致し、**0720 の2つの組合せ（上り線・下り線）は両方とも読まれます**（`G_intConbNum = 2`）。このため 0720 は1つの NDU のままです（決定40）。解析（解析用データ出力・SNAP の実行）はしていません。生成する NDU が変わると `tests/acceptance` が失敗するので、受入をやり直します。受入は `current.json` で行います。
- **データ確認図と荷重図の受入**（決定50・51、2026-10-18、`scripts/accept_jrsnap_figures.py`、記録 `tests/fixtures/acceptance/jrsnap_figures/record.json`、テスト `tests/acceptance/test_jrsnap_figures_acceptance.py`）：`current.json` から生成と同じ NDU と「基本ケース → 組合せ」を組み立て、本物の JRSNAP の runner（5.2-L03）の `figures` で描かせて、WebPier が受け取るページを測りました。荷重図が 0710 は8ページ・0720 は9ページで CASE の順に並ぶこと、ページが A4縦で色の画素が0、ページ番号がないこと、0720 の CASE-5・CASE-6 の両方に 480 が描かれていることを確かめました。生成する NDU か「基本ケース → 組合せ」が変わると `tests/acceptance` が失敗するので、`uv run --project "." --locked python -X utf8 scripts/accept_jrsnap_figures.py --overwrite` で受入をやり直します。荷重図は 5.2-L03 だけに対応します（5.3-L01体験版2 では JRSNAP の補助の中でアクセス違反になり、runner は失敗を返します）。

### Aggre-SE（プロジェクトXML）

0711・0721 の静的非線形解析の結果を Aggre-SE（structural-mcp の `Batch` サブモジュール、Docu-SE）で耐震照査するためのプロジェクトを、`post/線路方向.xml`・`post/線路直角方向.xml` に書きます（決定49、CONTEXT.md「耐震照査の入力」）。見本は Example2 の `10_線路(耐震)/P1_線路.xml`・`11_直角(耐震)/P1_直角.xml` です。同じ生成で Aggre-SE の runner がこの XML で照査し、その帳票が 0711・0721 の計算書になります（決定56）。

- 入力にするのは `耐震設計条件`（地域別・地盤区分）だけです。そのほかの条件は Example2 のプロジェクトと同じ WebPier の定めです。
  - スペクトルⅠ,Ⅱ両方、液状化指数 5<PL<20、M6.5以上の震源エリアなし、低減係数 α = 1.000、不整形性 η(x) は考慮しない
  - 全 Case で照査項目 ①〜⑨ のうち ④（破壊形態の検討）以外
  - 非線形部材（柱下端の M-θ）の部材照査タイプは 2（柱）、せん断耐力式は ①RC標準。損傷レベルの制限値は梁・柱・杭の順に復旧性 2/2/2、安全性 2/3/2
  - 直接基礎の制限値は空欄（Aggre-SE が自動計算）、帳票はカスタム仕様
- NDU から決まる値：直接基礎の照査位置は FootInfo の節点（線路方向 7、線路直角方向 8）、せん断スパン La は柱の断面の L（7600・10350 mm。直角方向は制御節点まで。起点側・終点側の桁の高さが違えば桁の慣性力で重み付けした高さ、決定65）、着目節点は 0（各 DB1 の着目点）です。
- 書式は Aggre-SE が保存するとおりです（Batch.exe 5.3.0.1 の `Input.GetXmlData` を Shift-JIS で書いたもの）。宣言は `encoding="utf-16"` ですが中身は Shift-JIS・CRLF で、ケースの配列は50件です。Aggre-SE の版が変われば書式を合わせます。
- 付帯JSONは XML の SHA256 と、参照する JRSNAP のフォルダーの SHA256（`aggrese_project.jrsnap`）を記録します。この XML で照査した計算書と runner の版（`seismic_check`）も記録します。
- **既知の差**：WebPier の NDU は直接基礎の照査のデータ（`ChokuKisoNum`・`CHOKU_KISO`）を持たず、runner は基礎照査に「いいえ」と答えるので、JRSNAP の基礎照査が書く `<DB1名>_Output_Chokukiso.csv` はできません。Aggre-SE はそのとき DB1 から直接基礎の照査値を求めます。作用（Vd・Hd・Md）は見本 10-26 と一致しますが、抵抗側（Rvd など）は違います（決定49）。

## Example2 との既知の差

現在の入力（`tests/fixtures/inputs/current.json`。`pre/input.json` も JRSNAP の解析設定のほかは同じ値）で Example2 と比べたとき、設計上残している差です。根拠はそれぞれのテストに書いています。

- **Example2 が丸めない中間値で印刷している箇所（0.01程度）**：WebPier は印刷された値から計算するので、Example2 の隠れた桁による差が残ります。例：08 p.8-4 の RB = 544.93（丸めない 272.4668 × 2）に対し 272.47 × 2.000 = 544.94。07 p.7-8・7-9 の 2851.85・7-11 の 2613.85 に対し 2851.84・2613.84。08 p.8-5 の 428.28 に対し 120.98 + 307.31 = 428.29。09 p.9-5 も同様です（`tests/calc/test_reaction_longitudinal.py`、`test_longitudinal_loads.py`、`test_transverse_loads.py`、`tests/export/test_frameweb_*loads.py`）。
- **シェルター荷重の集約**：WebPier にシェルターの機能はなく、入力はシェルター分を支承の D1・D2・S2 に集約し、風の受風高さは h4（9.433 / 10.767）、直角方向の地震時の桁慣性力は等価重心高 hs = M/H（2.952 / 3.066）に含めています。
  - 風荷重の H は Example2 と一致します（列車ありの起点側 197.00 など）。列車なしの 393.99・217.76 は Example2 の 394.00・217.75 と0.01違います（h4 を3桁に逆算したため）。風荷重の M は、シェルターを鉛直の偶力として扱わず高さに含めるので Example2 と異なります（0620 の合計 M は列車あり 2124.50・列車なし 4248.93、Example2 9-7・9-8 は 1001.33・2002.64）。この差はユーザーが許容しています（`tests/calc/test_reaction_transverse.py`、`test_transverse_horizontal.py`）。
  - 直角方向の地震時の桁慣性力は、起点側 6720.00 × 2.952 = 19837.44（Example2 19838）、終点側 2370.00 × 3.066 = 7266.42（Example2 7267）です。終点側の H は Example2 の 2360 に対し +10 kN（原本の独立反力 640 kN と集約した D1＋S2 = 400＋250 = 650 kN の差）で、線路方向の一致を保つため入力は調整しません。0720 の EQ1 は Example2 11-8 の H = 9080.00・M = 27105.00 に対し H = 9090.00・M = 27103.86 になり、原本の桁本体とシェルター偶力の内訳行は再現しません（`tests/calc/test_seismic_transverse_actions.py`）。
- **はりハンチの重心**：幅と奥行きが直線的に変わる立体の厳密な式 z = ∫z·b·w dz / ∫b·w dz を使い、0.389 m です。Example2 は錐台の式で 0.390 m（相似な断面でだけ厳密）で、0.001 m 違います（決定22、`tests/calc/test_reaction_self_weight.py`）。
- **0610・0620 の D1 の内訳**：0600 のはり重量（直方体＋ハンチ全体、1503.27 kN）を天端に置き、柱の線荷重と重なる H2＋H3 = 2.700 m を控除します。Example2 8-3 ははり 1190.70 と張出しハンチ 104.19 を置いて H2 = 2.00 m だけを控除するので途中の合計は違いますが、天端の N = 8299.53 は一致します（`tests/calc/test_longitudinal_loads.py`）。
- **フーチングの張出しの地盤反力（12.1 の 3)）**：原資料（`0700_線路フーチング.xls`）の柱前面の反力度 q2 は `qd2 + (qd1 − qd2)·L1/X1`（qd2 側の縁から L1 の位置の値）ですが、WebPier は q1 側の柱前面の値 `qd1 − (qd1 − qd2)·L1/X1` を使います（決定60、ADR-0001。両者が一致するのは L1 = X1/2 のときだけ）。安全性・使用性の列の W・x・M・Md・Vd・La が見本より大きくなります（例：線路方向 安全性 Vd最大 Md 760.74 → 799.16、Vd 675.13 → 728.89）。地震時の列（Case 4）は q2 を使わないので一致します。照合は独立の手計算 `tests/fixtures/example2/footing_hand.json` で行います（`tests/calc/test_footing.py`）。
- **フーチングの使用性の列（12.1 の 1)）**：FEMPython の反力の Vd は 19506.36／18049.95 kN で、見本の 19505.93 とは隠れ桁の丸めで 0.4 kN 違います（受入 `scripts/accept_footing.py` の許容差は使用性の Vd だけ 0.5 kN）。鉛直力が同じ2つの極値（水平力の向き違い）は |mz| の大きい行を採るので、Md は見本（3327.13／3056.25）と一致します（決定60）。
