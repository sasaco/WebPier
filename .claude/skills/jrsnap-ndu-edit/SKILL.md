# JRSNAP NDUの入力項目を編集する

## 編集前に確認すること

対象ファイル、入力キー、変更前後の値をユーザーの最新指示から特定する。ファイルごとに異なる指定を一括置換で混同しない。過去の事例の数値・件数は今回の既定値にしない。

`git status --short` と現在のファイルを確認する。既存の未コミット変更・ステージ済み変更を保持する。追加入力の訂正では、元の値が既に変更済みの場合があるため、現在の値から最新指定へ更新する。

項目の知見:

- コンクリート強度・梁寸法・主筋・せん断補強筋は [references/section-material-geometry-rebar.md](references/section-material-geometry-rebar.md) を読む。L3の形状コード15では、`SectConc<n>` の右辺第1フィールドがコンクリート圧縮強度、`SectInfo<n>` の第6が梁幅bw、第7が梁高さh、第8がスラブ厚tf。番号はカンマ区切りの1始まりで、`n` は `SectTitle<n>` で確認する断面番号。
- `SectFrangeJiku`（フランジの鉄筋）を扱うときは [references/sect-frange-jiku.md](references/sect-frange-jiku.md) を読む。
- 見本PDFと既存NDUを照合する場合、または直接基礎の `FootInfo`・`CHOKU_KISO`・支持件数を扱う場合は [references/example-pier2-seismic-verification.md](references/example-pier2-seismic-verification.md) を読む。解析用と照査用の別データ、PDF非掲載値、旧版からの保存時の補完項目を区別する。

計算表などへ値を転記するときは、元NDUのファイル名、断面番号、キーとフィールド番号、単位、転記先、換算方法を残す。梁高さ・材料強度のような転記値と、全幅・組数のような換算値を区別する。L3総括表への具体的な対応は [赤字入力セルの全参照元](../jrsnap-slab-shear-summary/references/input-sources.md) にある。

総括表の引張主筋選択ではユーザー指定に従い、**設計曲げモーメントMdmaxが負なら上端主筋（上側引張）、正なら下端主筋（下側引張）**とする。L3が全て負だったことを一般化しない。段数・距離の原点も選択側に合わせ、転記先の「上端／上面から」「下端／下面から」の表記と計算をそろえる。詳細は [断面データの資料](references/section-material-geometry-rebar.md) と [正負切替の手順](../jrsnap-slab-shear-summary/references/tension-side.md) を読む。これは転記側の選択規則であり、Mdmaxの符号に合わせてNDU自体の配筋を反転・変更する指示ではない。

## Shift-JISを保持する編集

`.ndu` はShift-JIS。表示の文字化けをファイル破損と取り違えず、読み取りにはCP932を明示する。PowerShellの既定エンコーディングで `Set-Content` / `Out-File` に書き戻さない。

ASCIIのキーと数値だけを変更する場合は、`[IO.File]::ReadAllBytes()` で読み、バイト列へ限定置換する。この環境で確認済みの方法は、`[Text.Encoding]::GetEncoding(28591)`（Latin-1）で全バイトを可逆に文字へ対応付け、ASCII部分を置換して同じEncodingの `GetBytes()` で戻す方法。これはファイルの文字コード変更ではない。日本語の表示・編集にはこの中間文字列を使わない。

日本語を編集する場合はCP932の例外フォールバックを用いて変換不能文字を検出する。対象外のバイトを保存前後で比較し、全体の再エンコードによる変化がないことを確認する。

行頭の完全なキー形式とカンマ区切りのフィールド位置を指定して置換する。ファイル全体への `16,250` のような無条件置換は避ける。元の改行、末尾改行、空白、行順、ヘッダーを保ち、変更不要の行を再構成しない。

## 検証して保存する

1. 保存前のバイト列を保持し、実データから置換候補・件数を確認する。複数ファイルなら、全対象の変更案を先に検査する。
2. 変更した各行が指定キーに属し、指定フィールド以外が同一であることを確認する。対象外の行はバイト単位で一致させる。件数が想定と違えば、対象キーや現在値を調べてから進める。
3. 読み取り後にファイルが他の処理で変更されていないか再確認し、`[IO.File]::WriteAllBytes()` で保存する。保存後に再読込して予定したバイト列と一致することを確認する。
4. `git diff --check` と差分を確認する。対象外のファイルを含む一括作業では、対象外ファイルのSHA-256が不変であることも確認する。ステージ済みの変更があるときは、作業ツリーの今回の差分と既存の差分を区別する。

ファイル単位の変更件数と検証結果を報告する。文字列置換と差分検証は、JRSNAPによる読込・解析の検証とは区別する。`.ndu` 編集だけでは `.ndt` や解析結果は更新されない。

アプリで開いて保存する作業は [jrsnap-input-open-save](../jrsnap-input-open-save/SKILL.md)、解析実行は [jrsnap-input-launch](../jrsnap-input-launch/SKILL.md) を参照する。

## 知見を更新する

新しく確認したキーの構造、画面項目との対応、編集上の注意、検証方法をこのスキルに反映する。項目固有の説明は `references/` に置き、このファイルからリンクする。

資料には根拠と確認範囲を残す。ユーザーから教わったこと、ファイルで観測したこと、マニュアル等で検証したこと、未確認事項を区別する。個別案件の指定値・観測件数を一般仕様にしない。訂正は該当記述に反映し、矛盾する指示を増やさない。
