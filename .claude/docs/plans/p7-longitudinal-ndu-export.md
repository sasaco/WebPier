### Purpose

0710の線路方向荷重を計算する同一実行内の情報を用い、JRSNAP 5.2-L03用の `P7橋脚/post/線路方向.ndu` を繰り返し生成できる機能を追加する。PDFに表示した丸め値を読み戻さず、読み込んだ入力、0500基礎計算、0710の形状・作用、配筋情報から出力する。

ユーザー確認済み: **単発ファイル作成ではなく出力機能の追加、対象版はJRSNAP 5.2-L03**。

ユーザー回答と追加調査による方針:

1. **回答済み**: 見本と同様、柱下端0.010 mのみM-θ部材、他部材は剛域、基礎は並進ばね＋非線形回転ばねとする。寸法・材料・配筋・作用・地盤値はP7から取得する。
2. **回答済み**: 初回も現在の配筋を含む入力を採用し、0710とNDUを同時生成する。保存済み0710作成後の配筋更新を含める。
3. **ユーザーの追加指示で訂正**: Df・γ2は0500の地盤条件と0710の採用水位から自動算出する。見本08_線路.pdf 28頁の明示式を確認したため、必須手入力欄の追加案を撤回する。P7はDf=4.7、γ2=(2×18+2.7×8)/4.7=12.255319…、見本同様の小数第1位採用案は12.3。

導出根拠・適用条件・丸めは[Df・γ2調査](../research/p7-longitudinal-ndu-soil-derivation.md)に記録した。回答済みのモデルと入力世代を再質問しない。未完成の無支持モデルを成功扱いで出力する別モードは今回実装しない。

モデル配置の承認を、未確認の解析定数まで承認されたことに拡張しない。Step 1で作る完全なprofile表について、既に承認された値・5.2の書式要件・P7由来値・新たな工学的選択を区別する。既存承認を取り直す必要はないが、新しい工学的選択が残る場合は具体的な表を提示して確定するまでStep 2へ進まない。

#### Export contract

- `--jrsnap` なし: 既存動作のまま。0710単独2件、all16件。NDU用の対応範囲検証が既存帳票生成を妨げない。
- `--stage 0710 --jrsnap`: PDF/JSON/NDU/専用sidecarの4件を同一入力から作成・検証し、一括公開。
- `--stage all --jrsnap`: 既存16件＋NDU2件の18件を一括公開。各FrameWeb manifestの意味は維持し、NDU側にも同じpublication IDを持たせる。
- `--jrsnap` とそれ以外の単独stage: 明示エラー。通常の他stageは既存NDUに触れない。
- `--post-dir` と `--overwrite` は既存規則を共用。任意output指定時に本番postへ出力しない。生成NDUの手編集は自動マージせず、上書き指定時に生成物として置換する。
- 2026-10-17の追加指示「入力画面に追加する」により、せん断用部材係数Vcd/Vsd/Vddと粗骨材最大寸法の4項目だけをrawの専用設定とGUIへ追加する。JRSNAP未選択時は旧入力を維持して受理し、選択時は4項目の存在・型・有限値・範囲を検証する。初期値/今回実値はユーザー回答「見本値を初期値にして作成する」でVcd2.0/Vsd1.3/Vdd1.8/Dmax25 mmに確定した。Df/γ2は手入力欄を設けずprofile内の導出規則をschema1として版管理し、`effective_embedment_m` と `overburden_effective_unit_weight_kn_m3` は計算結果として保持する。元入力パス、0500の表層、0710の水位ケース、区間長、単位重量、丸め前値とNDU採用値をsidecarへ記録する。
- 初期対応は一つの表層＋支持層、支持層上面に基礎底面、左右同じ土被り、Df>0、**0 < hw2 < Df**の場合。非有限値・入力不足、左右土被り差が1e-9 mを超える場合を先に拒否し、その後 `H6+H5+min(df1,df2)` と同一実行0500の表層厚の差が1e-9 m以内であることを確認する。両元値と差・比較許容差を記録する。
- 水位範囲を検証してから水中区間=hw2、湿潤区間=Df−hw2で厚さ加重平均し、γ1は支持層水中単位重量を採用する。水位をclampして未対応条件を通さない。hw2=0、hw2=Df、底面以下、地表超過、多層・傾斜土被りはv1では明示拒否し、手入力迂回を作らない。境界を後に対応するには別の根拠確認と仕様改訂が必要。
- γ2は丸め前を保持し、NDU採用値のみ既存Excel ROUND互換で小数第1位へ丸める案とする（見本11.6の再現、P7は12.3）。Dfは元の長さ精度を保持する。PDFの表示から数値を読み戻さない。
- 入力型・有限値・範囲は5.2仕様で確認し、0が許容される項目では未入力と0を区別する。出力対象外の入力セクションを正規化し直さない。

#### 入力・計算ハッシュと正式バイトの契約

- `raw_input_sha256` はその実行で一度だけ読み込んだ入力ファイルの**全バイト**のSHA-256。JRSNAP名前空間を除外しない。0500/0710/NDU/sidecarは同じ値へ結び付ける。
- 初回入力はユーザーが選んだ現在配筋の原本全バイトSHAに固定する。追加指示の4設定を確定後にrawへ保存する際は、調査時スナップショットとの意味差分がその4項目だけであることを確認する。新しい全バイトSHAのスナップショットを受入起点として別保存し、`origin_input_sha256` と `raw_input_sha256` はその新SHAで一致させる。調査時SHAの証拠は上書きせず残す。開始後の入力変更を検出したら古い承認スナップショットと無言で合成せず、対象入力を更新して受入をやり直す。JSONキー重複を拒否する。
- 計算スナップショットのSHAはcanonical schema1とし、0500/0710のJSON互換dict**全体**を `json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=False, allow_nan=False)` でUTF-8化して算定する。除外フィールドなし。保存されたJSONファイル自身のSHAとは別名で記録する。
- 正式に公開するNDUは、実装したexporterの決定的な出力バイト。JRSNAPが保存し直したバイトを正式版へ差し替えない。アプリ検証は複製だけで行い、exporter出力SHA・第1保存SHA・第2保存SHAと意味上の差分を検証記録に残す。
- 正式sidecarの `app_read_verified` は「この生成run内で実アプリ読込を行った」の意味とし、実行時にJRSNAPを呼ばない本機能では**初回を含め常にfalse**。初回受入は別の検証記録として提示し、sidecarへ後付けでtrueを書き込まない。
- 受入記録は `.agents/docs/research/p7-longitudinal-ndu-acceptance-<publication ID>.json` に保存する非製品の検証資料。正式出力4/18件や共通公開トランザクションには加えない。origin/raw入力SHA、0500/0710計算SHA、全候補の期待パスと保存SHA（0710 PDF/JSON、NDU、sidecarを含む）、profile版と実装ソースSHA、設定schema、Df/γ2の値・出典、publication ID、対象版、検出したJRSNAP実行ファイル/アセンブリの版・ビルド・SHA、検証日時、第1/第2保存SHA、意味照合結果を記録する。NDU SHAやファイル名だけが一致する別入力世代へ流用しない。
- 初回受入スクリプトは生成候補を保持し、実アプリへは複製だけを渡す。候補全体と入力・profileの不変を確認し、検証済み記録を保存できた後で共通公開処理へ進む。公開後に全保存SHAを再確認して記録を完了状態にする。記録の最終更新だけが失敗した場合は成果物を取り消さず「公開済み・受入記録未完了」として失敗終了し、完了と報告しない。`--finalize-receipt <record>` で記録内の全期待パス/SHA・入力/profile同一性を再照合して記録だけを完成できるようにする。
