# .claude\docs\Example橋脚2: 線路方向 PDF と FrameWeb JSON の対応調査

調査日: 2026-10-16。実装前の読取調査。原本・入力・既存 JSON は変更していない。

対象:

- `.claude/docs/Example橋脚2/08_線路.pdf` (32 ページ)
- `.claude/docs/Example橋脚2/08_線路/frameWebForJS.json`

この PDF では物理ページ n と印刷ページ `8 - n` が一致する。以下の `pN` は物理ページを表す。p1〜11 の入力条件を全文抽出し、p1〜11 の図表を PNG に描画して目視確認した。作業ファイルは `tmp/p7-frameweb-plan/example/`。PDF から JSON の数値への対応は確認済みだが、FEMPython のデータ解釈は別途ソースコードで確認する必要がある。

## 1. 全体構造

JSON のトップレベルは `node`, `fix_node`, `member`, `element`, `load`, `define`, `combine`, `pickup`, `three`, `dimension`。

| PDF の情報 | JSON の場所 | 件数・対応 |
|---|---|---|
| p1 (8-1) 骨組図 | `node`, `member` | 6 節点・5 部材 |
| p1 フーチング底面ばね | `fix_node.1`, `fix_node.2` | 長期・短期各1節点 |
| p2 (8-2) 断面諸元 | `element.1.1`, `element.1.2` | 柱・剛域 |
| p3〜5 計算、p6〜8 荷重図 | `load.1`〜`load.20` | 基本荷重20ケース |
| p9 (8-9) 基本ケース・Defineケース | `load.*.fix_node`, `define` | 支持条件参照・正負ケース |
| p10 (8-10) 組合せケースと荷重係数 | `combine.1`〜`combine.16` | 16行と一致 |
| p11 (8-11) 抽出ケース | `pickup.1`〜`pickup.8` | 8行と一致 |

`fix_member`, `joint` はトップレベルに存在しないが、全 `load` にその参照値がある。`fix_member` は `fix_node` と同値、`element=1`, `joint=1`, `LL_pitch=0.1`, `rate=1` は全荷重共通。これらのソフト用フィールド、`row`, `three.camera`, `dimension=2` は PDF に直接数値対応する表がない。

## 2. 座標・部材

PDF p1 の寸法から、フーチング底面を y=0 として上向き正に累積する。全節点 x=0、z=null。

| 節点ID | JSON `node.ID.y` (m) | PDF p1 との対応 |
|---|---:|---|
| 1 | 10.30 | 全高 2.00+0.70+4.90+2.70 |
| 2 | 8.30 | 梁下面、高さ 10.30-2.00 |
| 3 | 7.60 | ハンチ下面、高さ 8.30-0.70 |
| 4 | 2.70 | フーチング上面 |
| 5 | 1.35 | フーチング重心 (p2 `ye=1.350 m`) |
| 6 | 0.00 | フーチング底面・ばね取付点 |

`member.1={ni:1,nj:2,e:1,cg:null}`、2は2→3、3は3→4、4は4→5、5は5→6。部材1〜3は柱 `e=1`、4〜5は剛域 `e=2`。部材の i→j は全て上から下。

p1 図の水平寸法には注意が必要。柱2.700と左右2.150を足すと7.000で、p3のフーチング荷重も幅7.00を使用するが、図下の寸法線は3.000+3.000=6.000と記載されている。JSON は鉛直1本骨組のため、この幅表記差は節点座標に現れない。P7に6.0を流用する根拠にはできない。

## 3. 材料・断面・ばね

| 項目 | PDF | JSONパス・値 |
|---|---|---|
| 柱のE | p2 `2.65×10^7 kN/m²` | `element.1.1.E=26500000` |
| 柱のA | p2 `4.50×2.70=12.150 m²` | `element.1.1.A=12.15` |
| 柱のI | p2 `4.50×2.70³/12=7.38113 m⁴` | `element.1.1.Iz=7.38113` |
| 柱の名称 | p2 柱 | `element.1.1.n="柱"` |
| フーチング | p2「すべて剛域とする」 | `element.1.2.n="剛域"`, `A=1000`, `Iz=1000` |
| 剛域E | PDFは別Eを指定していない | `element.1.2.E=26500000` |

両断面の `Xp=0.00001`、`G=J=Iy=null`。剛域のA/Iを1000にすること、Xpの数値はPDFに記載なし。例題のソフト上の設定として分類し、設計値の抽出結果と混同しない。

`fix_node.1[0].n="6"`, `row=1` が長期、`fix_node.2[0]` が短期。p1の表から以下のとおり直接対応する。

| JSON成分 | 物理量 | 長期 `fix_node.1` | 短期 `fix_node.2` | 単位 |
|---|---|---:|---:|---|
| tx | せん断ばね Ks | 4,262,769 | 8,525,475 | kN/m |
| ty | 鉛直ばね Kv | 12,788,244 | 25,576,488 | kN/m |
| rz | 回転ばね Kr | 52,218,663 | 104,437,326 | kN·m/rad |

`tz=rx=ry=null`。短期Ksは長期Ksの厳密な2倍ではない (差63)。PDFの指定値を採用しており、自動で「短期=2×長期」にしては例題を再現できない。

### 4.1 固定死荷重と二重計上防止

p3から:

- 柱分布荷重: 4.50×2.70×24.5=297.68 kN/m。
- フーチング: 24.5×7.00×9.00×2.70=4167.45 kN → node5。
- はり1190.70、ハンチ104.19、RB=5740.00、RC=1860.00の合計=8894.89 kN。
- 天端荷重: 8894.89−297.68×2.00=8299.53 kN → node1。
- 天端M: 5740.00×(-0.325)+1860.00×0.675=-610.00 kN·m → JSON rz=+610。

分布荷重は梁の高さ部分を含む柱モデル全長7.60mに載せるため、梁と重なる2.00m分を天端集中荷重から控除している。P7の天端集中荷重を組み立てる際、この控除の有無をP7自身の計算表・生成ロジックで確認する必要がある。

### 4.2 丸め

JSONはPDFの最終表示値を採用している。例: I=7.381125を小数5桁の7.38113、q=297.675を297.68。

再計算時に既に丸められた値から元の精度を推定しない。複線列車荷重1134.77は単線表示567.39の2倍1134.78と0.01異なる。またp5の複線衝撃の表示成分120.98+307.31=428.29に対し、合計表示とJSONは428.28。p5の単線衝撃も272.47×表示係数0.245=66.75515だが、PDFの成分表示は66.75。元の内部精度・丸め手順はこのPDFだけから一意に復元できない。

## 7. 不一致とソフト用定数の一覧

確定した資料間差異:

1. Case14,18,20のばね番号はPDF=1、JSON=2。
2. `load.15.symbol`, `.19.symbol` はJSON `1.0LR+1.0B`、PDF `1.0LR+1.23B`。
3. `load.16.symbol` はJSON `1.1LR+1.0B`、PDF `1.1LR+1.23B`。
4. `load.17.symbol` はJSON `1.0LR+1.1B`、PDF `1.0LR+1.35B`。
5. Case18,20のJSON nameは「ロングレール+制動」だが、PDF基本ケース表ではロングレール縦荷重のみ。
6. PDF p7の列車荷重M矢印は反時計回りに描かれ、同ページの雪・p6の死荷重・p8の衝撃荷重の時計回り矢印と逆。数値としては全てJSON `rz=-M表値` で一致する。矢印だけを正解として符号を再解釈しない。
7. p1フーチング幅の図内寸法7.0相当と下側寸法6.0が不一致。

PDFに根拠数値がないもの:

- 剛域A=Iz=1000、両断面Xp=1e-5。
- nullを含む未使用3D成分、`cg`。
- `LL_pitch=0.1`, `rate=1`, `row`。
- `fix_member` / `joint` の参照値（トップレベル定義なし）。
- `three.camera={x:0,y:-1.0000000000509601e-5,z:9.999999999994998}`。

## 8. P7実装計画へ渡す注意

1. 例題を入力項目の対応確認に使い、基本ケース番号・支持条件・形状をP7へ固定コピーしない。
2. 生成ロジックのあるP7アプリでは、PDF描画文字列からの恒常的OCRより、PDFと共通の計算結果・型付き入力をJSONへ変換する経路を優先する。最初の照合では指定PDFの表示値との対応表を残す。
3. 節点yはP7自身の梁・ハンチ・柱・フーチング高さから作る。自重は天端集中荷重と柱分布荷重の重複を点検する。
4. N/P/Mの符号変換、水平荷重の正負Define、部材局所xを個別に検証する。
5. 支持条件は基本ケースごとにPDFと照合し、長期/短期のラベルだけから数値2倍を仮定しない。
6. 荷重値、支持値、組合せ、pickupを数値/参照検査し、空荷重ケースと空行のソフト互換性を確認する。
7. 例題を再現検証に用いる場合、上記の既知不一致を差分台帳で説明する。PDFとJSONが完全に同値であると主張しない。

現段階で未確定なのは、ソフト用フィールドの厳密な必須性、正負Define/複数支持条件を含むcombineの計算仕様、PDF内不一致の設計者意図である。P7の値とソフト仕様の調査により実装前に解決する。
